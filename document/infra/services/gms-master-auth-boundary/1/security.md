## Scope and design boundary

This bundle covers the private `POST /internal/v1/license/current` call from the existing partner process (temporarily hosting the staged master tRPC router) to auth, the public Nginx `/api/master/trpc` route and denial of `/internal/*`. ADR-0031 and SA review revision 1 authorize the scoped local-dev Compose/Nginx changes in this bundle. The present config is a draft only until backend app adapters and runtime checks are complete. It does not authorize service rename, gateway removal, production changes, cutover, push or deployment.

The selected topology is a single-host Docker Compose bridge design. The scoped local-dev overlay now declares these network roles:

| Candidate network | Members | Purpose and guardrail |
|---|---|---|
| `auth-master` (`internal: true`) | auth + current partner/master | Private service-to-service path for license decision. Nginx is not a member. Auth retains its separately required DB and license-server paths. |
| `master-web` (`internal: true`) | Nginx + current partner/master | Nginx forwards only public `/api/master/trpc` to partner/master. Nginx also stays on the existing frontend/auth/legacy upstream network as required during preview. |
| Existing `partner-api` (`internal: true`) | gateway + partner/master | Preserve gateway-to-partner legacy rollback until callers have migrated and zero legacy use is observed. |
| Existing `partner-db` (`internal: true`) | PostgreSQL + partner/master | Preserve current partner schema access. Backend owns DB role provisioning. |
| Existing `default` | Current consumers as currently declared | Auth currently needs PostgreSQL and outbound license-server connectivity through its attached network(s); this must be mapped explicitly before detaching or replacing `default`. Avoid broad, accidental membership for the new endpoint. |

The draft overlay attaches auth to `default` plus `auth-master`; current partner/master to `partner-api`, `partner-db`, `auth-master` and `master-web`; Nginx to its existing `default` plus `master-web`. All existing services, volumes and rollback networks remain declared. Nginx waits for partner's existing `service_healthy` readiness check. Auth's broad host port is reset in this local overlay; partner/master remains unpublished. Existing gateway, frontend and PostgreSQL host mappings are preserved for this dev stack and are not an approved production target.

`internal: true` isolates external connectivity for that network, but it is not a port ACL or caller identity control. Docker user-defined bridge members can communicate to all listening container ports on that shared bridge; Docker host/daemon administrators remain trusted and can inspect or connect to container networks. Auth is currently multihomed on `default` and would remain so unless a separately designed change maps its DB and outbound paths. Therefore the dedicated bridge narrows the intended master path but does **not**, by itself, prove that only master can open a TCP connection to auth. The dedicated high-entropy `MASTER_AUTH_SERVICE_TOKEN`, strict request/session binding and auth-side constant-time verification are the actual caller authorization. If SA requires network-level exclusive reachability, change the contract/topology to use a separately bound listener or another explicitly approved mechanism; Compose bridge membership alone cannot provide that guarantee for a multihomed auth process.

The auth-master bridge must remain single-host. Do not stretch it across machines or rely on plaintext bridge HTTP outside the trusted Docker host. The proposed internal HTTP request is defensible only under the approved same-host boundary plus the application credential; multi-host communication requires SA-approved TLS/service identity and network design.

### Nginx policy

- Add an explicit master location to `api-master:3201` only for `/api/master/trpc` (or the SA-approved exact prefix), preserve the URI as required by the app router, and keep `X-Request-Id`, Host and trusted proxy metadata consistent. Nginx `proxy_pass` URI handling depends on whether a URI suffix is specified; validate path preservation with the exact runtime config.
- Keep an exact `/internal` deny and a higher-priority prefix deny for `/internal/` returning 404, ahead of fallback `/` and any proxy regexes. The existing preview regex blocks lowercase `/internal` and `/_storage`; future config must retain that behavior and must not create a more specific allow/proxy location. Verify normalized paths and encoded separators with negative HTTP checks.
- Nginx must not join `auth-master`. Nginx can reach auth's public auth API through its public web network but must not proxy any private endpoint. Route-denial tests must prove the request never arrives at auth, not only that auth returns an error.
- Preserve same-origin cookie/CSRF behavior; no browser route, CORS exemption or Nginx auth subrequest is added for the private license call. Do not cache `POST`, auth, master, license or user-specific responses.
- For this local preview, bind Nginx to `127.0.0.1:8080` and remove direct host publication of auth and partner/master. Gateway, frontend and PostgreSQL mappings are retained for existing local tooling in this narrowly scoped overlay; moving them behind Nginx or binding PostgreSQL to loopback requires a separate parent-owned compatibility decision.

## Secret delivery and application compatibility

- `MASTER_AUTH_SERVICE_TOKEN` is a dedicated random high-entropy opaque secret, separate from `PARTNER_SERVICE_TOKEN`, CRM, Better Auth, JWT signing and license-server secrets. Never include values in this document, `.env.example`, Dockerfile, image layer, command line, request/log output or `docker compose config` evidence.
- Scoped local-dev delivery uses the file-backed Compose secret `master_auth_service_token`, granted only to auth and partner/master, mounted at `/run/secrets/master_auth_service_token`. `MASTER_AUTH_SERVICE_TOKEN_SOURCE` is a Compose interpolation containing only the host file path; that source must be outside the repository/build context. It is not passed to the app as an environment variable. `MASTER_AUTH_SERVICE_TOKEN_FILE=/run/secrets/master_auth_service_token` is configured on both services. Auth requires `AUTH_ACCESS_JWT_ISSUER` and `AUTH_ACCESS_JWT_KEYS` for local signing; partner requires the same issuer and `FRONTEND_URL=http://localhost:8080` for validation. Partner fetches public keys from the existing `AUTH_SERVICE_URL=http://backend-api-auth:3101` base at `/api/auth/jwks`. Compose uses required interpolation for signer values so an unset local signer fails configuration; no private-key value is documented here. Partner also requires `MASTER_AUTHZ_DATABASE_URL`; the reader URL is set only on partner and has no fallback. Local Docker Desktop file-sharing/permission behavior and app UID access still need runtime validation; use only disposable development credentials in the local mock profile.
- Compose secret mounting does not automatically create an application environment variable. Backend must implement supported file reading, trim one trailing newline only, validate length, fail startup/endpoint readiness closed on missing/empty material, compare in constant time, and redact the header/body from logs and error telemetry. Confirm compatibility with runtime UID 1000 and path permissions. Do not enable the endpoint until both services consume the same secret file successfully.
- Compose file secrets from local files are bind-mounted, not an encrypted remote secret vault. Host/daemon administrators and backup processes that can read the host source file remain in the secret trust boundary. Production secret creation, delivery, rotation and recovery need a separate approved operational runbook. Replacing a file-backed secret may require recreating the service to remount it; never rotate the live key during this draft.
- Credential rotation should be staged only after approved reader behavior: provision new secret to both services, allow a bounded dual-key overlap only if backend contract supports it, switch sender, observe auth decisions, then revoke old key. ADR-0031 presently specifies one token; dual-key overlap is not approved. If single-token rotation requires simultaneous auth/master restart, use the existing legacy gateway route as rollback and keep data volumes untouched.

## Storage, init and data protection

- This delta has no new mount, storage, init job or database migration. Existing partner `partner-storage` and PostgreSQL `postgres-data` must remain untouched; auth storage remains as currently mounted when auth is brought up.
- Auth/master DB role provisioning and grants are owned by backend. The SA delta separates the identities: `MASTER_AUTHZ_DATABASE_URL` uses dedicated non-owner `gms_master_authz_reader`, with `SELECT` on `auth.current_authorization` only; it has no DML. Existing `PARTNER_DATABASE_URL` and Prisma client/role remain unchanged for existing partner customer/vendor/company-profile/stone domain DML. This ticket adds no DML grants to either identity. The authz reader must not access auth base/license/refresh/sequences, `stone`, migration tables, create/owner privileges or broad role membership. A DB administrator/migration role provisions the exact view-only grant; no `f1_user`/superuser runtime shortcut.
- Startup dependency should distinguish process start from readiness: auth needs Postgres readiness; partner/master needs Postgres and auth endpoint readiness before serving protected requests. Keep health probes credential-free and avoid showing secret values. Existing startup commands run migrations at app start in production image; ADR-0031's required additive roles should be applied by a controlled one-off/DB-owner step, not by broadening runtime startup privileges.
- Rollback disable order: stop using the mounted master route; return browser calls to existing Nginx/Next/gateway path; disable the auth private endpoint and revoke the dedicated credential and master read-only grants. Leave auth decision tables, customer/vendor rows, photos, files, database and storage volumes intact. Re-enable a previous route only while schema compatibility is verified. No volume deletion, database reset or image prune is part of this bundle.

## Capacity

- This SA delta creates no process/container and specifies bounded auth/master pools of at most 5 each. It adds one private request per protected master operation with a 1.9 s auth handler limit, 2.0 s caller deadline and existing 1.5 s license upstream timeout. The code must not hold a database connection across the network wait. Network bridges and Nginx route config have no declared container memory/CPU cap cost; request CPU/RSS/latency still require measurement.
- Current ADR-0024 production caps: PostgreSQL 1024 MiB/0.60 vCPU; auth 512 MiB/0.30; gateway 384 MiB/0.25; partner/master 384 MiB/0.25; frontend 640 MiB/0.30. Total **2944 MiB / 1.70 vCPU**, leaving approximately **1152 MiB / 0.30 vCPU** host headroom on a 4 GB/2-vCPU machine. No new cap is added by this draft. These are caps, not measured usage.
- Current merged development Compose declared limits: PostgreSQL 1024 MiB/0.60; auth 1536 MiB/1.0; gateway 1536 MiB/1.0; partner 1024 MiB/0.25; frontend 1536 MiB/1.0; Nginx 64 MiB/0.10. Aggregate maximum **6720 MiB / 3.95 vCPU** if all run. This is a workstation watch profile, exceeds the production host and MUST NOT be used as the 4 GB deployment profile. The runtime snapshot above had only partner + PostgreSQL up (declared caps 2048 MiB / 0.85 vCPU), but host capacity is not recorded here.
- Target GMS spec's full `db-local + fs` profile is a different future architecture: 3040 MiB stated service caps and ~1056 MiB arithmetic headroom; it is not implemented by current Compose and is not approved by this ticket. Customer DB/file profile, full CPU budget, host RAM/CPU/disk, load and production image RSS/p95 remain unmeasured. Do not claim capacity from YAML sums alone.
- Before cutover, measure auth and master RSS/CPU under concurrent license calls, p95 and timeout rate, DB connection occupancy (including migration/admin reserve), slow upstream behavior and Nginx request path. Verify no cross-request pool/transaction held while awaiting license. If limits/p95 fail, stop and return a bounded SA capacity revision; do not increase deadlines or limits implicitly.
