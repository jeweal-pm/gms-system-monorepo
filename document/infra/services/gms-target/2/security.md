## Current evidence and why the old containers remain

The current merged dev stack still declares `postgres`, `backend-api-auth`, `backend-api-gateway`, `backend-api-partner`, and `frontend`. Its base file publishes Postgres 5432, auth 3101, gateway 4000, and frontend 3000; partner stays private. The dev override runs source watchers from one shared `f1-system-dev:local` image. `frontend/src/providers/app-providers.tsx` still calls `/api/trpc`; Next proxies `/api/trpc` to gateway `/trpc`, `/api/auth` to auth, and `/api/v1` to gateway. Gateway still owns the shared tRPC router, and partner still serves private `/internal/*` procedures. Auth has a public `/api/auth/jwks` prototype but the new access-token and domain cutover tasks are open. A container-name substitution would conceal these dependencies and does not deliver target behavior.

There is no `api-inventory`, Redis, worker, Garage, or target Nginx service in this checkout. ADR-0025 explicitly keeps the gateway during per-procedure parity and rollback; ADR-0027 keeps partner/stone data in existing schemas until a separate measured migration. The selected first inventory feature and real license-server remain unresolved. These are implementation gates, not reasons to leave the local GMS ingress preview invisible.

## Exact local preview topology

Use a **local-only** Compose overlay or dedicated profile, serially owned by the parent, atop the existing dev stack. Add one `nginx` service using the `nginxinc/nginx-unprivileged:1.30.6-alpine3.24` candidate, internally listening on 8080 and published only to `127.0.0.1:8080`. Keep the existing dev containers and source-watch mounts. Keep the current PostgreSQL named volume and auth/partner storage named volumes; do not copy, rename, prune, or reinitialize them for this preview. The preview runs mock license mode as the existing dev override specifies. Do not expose mock protected-route decisions as production proof.

| Service in preview | Purpose and local DNS:port | Host publication | Storage / network |
|---|---|---|---|
| `nginx` (new) | Browser ingress; `frontend:3000` for all active routes | `127.0.0.1:8080:8080` only | Read-only config; only frontend-facing network; no DB or storage mount yet |
| `frontend` | Existing Next pages, SSR and `/api/auth`, `/api/trpc`, `/api/v1` proxy routes | Existing dev publication remains during preview, ideally loopback-bound after port-contract review | Needs DNS to auth and gateway; no direct DB |
| `backend-api-auth` | Better Auth, sessions, JWKS prototype, current license check | Existing dev 3101 for diagnostics only; loopback-bound when old tools are reviewed | DB `postgres:5432`, auth photo volume; remote license egress only in remote mode |
| `backend-api-gateway` | Existing tRPC router and old REST facade | Existing dev 4000 for diagnostics only; loopback-bound when callers are reviewed | DNS to auth 3101 and partner 3201 |
| `backend-api-partner` | Existing private customer/vendor/company/stone APIs; master implementation source | None | Private gateway and DB networks; existing company-logo volume |
| `postgres` | Existing PostgreSQL `18.6-alpine`, local DB | Existing dev 5432 for Prisma Studio only; loopback-bound after host-tool review | Preserve existing `postgres-data` volume and PG18 parent mount `/var/lib/postgresql` |

For the **first visible preview**, Nginx sends `/api/auth/*`, `/api/trpc/*`, `/api/v1/*`, `/_next/*`, and `/` unchanged to `frontend:3000`; `/internal/*` and `/_storage/*` are rejected at the edge. `proxy_pass http://frontend:3000;` without a URI preserves the original request path. Sending `/api/trpc` directly to gateway would fail because gateway mounts `/trpc`, and sending `/api/master` to partner would expose its private service-token APIs. Nginx forwards Host, scheme, real client IP only from trusted upstreams, and an `X-Request-Id`; it limits sign-in by the actual `/api/auth/sign-in/username` path. Auth's `FRONTEND_URL` trusted origin and `AUTH_BASE_URL` must be set/tested for the preview's `http://localhost:8080` origin before browser login, because the current env points at the old frontend port or direct auth. Keep the previous origin usable only as an intentional local transition path.

The first preview proves only the ingress shape and existing UI at a new URL. It still shows old container names in Docker because old processes are serving requests. Present that fact clearly in the UI/handoff. The route prefix and startup probes must be checked with real login/logout, activation, existing tRPC pages and Next hot reload before defaulting users to the new URL.

## Target service map and exact cutover order

| Stage | Public route after stage | Required application evidence | Old process retirement |
|---|---|---|---|
| A — local ingress preview | Nginx to Next for all active paths | Same-origin cookies, CSRF/Origin, existing route parity, request IDs; mock mode labeled | None |
| B — auth route | Nginx `/api/auth/*` directly to `api-auth:3101`; Next serves remaining active paths | GP-AUTH-01..06, complete Better Auth cookie/JWKS/refresh/license behavior, security reviews and real license-server gate for protected production paths | Legacy Next auth proxy kept as rollback until parity; may then remove |
| C — master by procedure | Nginx `/api/master/*` to `api-master:3201`; frontend moves selected typed clients | GP-MASTER-01..04, exact action grants, local JWT/live view/license verification, feature parity and data checks | Gateway and old `/api/trpc` remain until zero callers, then remove |
| D — selected inventory feature | Nginx `/api/inventory/*` to `api-inventory:<approved port>` | Separate approved initial vertical slice, schema/roles, posting tests and capacity | No inventory placeholder container before approval |
| E — heavy/storage feature | Private Redis/worker and selected fs/S3 components | Separate feature/profile approval, full resource/backup evidence | No automatic activation from the GMS diagram |

At target completion, Compose service names/images should be `nginx`, `frontend`, `api-auth`, `api-master`, `api-inventory` (when selected), PostgreSQL for `db-local`, and Redis/worker only when triggered. Only Nginx publishes host 80/443. The old `backend-api-gateway` and `backend-api-partner` names disappear only when their code and traffic are actually migrated; `api-master` may use adapted partner source and initially retain `partner`/`stone` schemas, per ADR-0027. No public `/internal/*` location is permitted. Nginx routes `/api/auth/`, `/api/master/`, `/api/inventory/` without rewriting the prefixes; static immutable assets alone receive long caching. Authorized `/_storage/` delivery and `/public/` files enter only with an implemented fs adapter, bounded upload path and read-only Nginx mount.

## Security, capacity and operations handoff

For the local preview, use the image candidate above, non-root port 8080, read-only configuration, `init: true`, no added capabilities, `no-new-privileges`, bounded logs and a health probe. Try a read-only root with a small writable `/tmp` only after `nginx -t` and startup show the image entrypoint's exact needs. Do not put credentials in the Nginx config or render resolved Compose secrets into evidence. TLS at host 443, ACME/certificate rotation and trusted external proxy CIDRs belong to the later customer deployment; localhost HTTP preview is not production ingress acceptance. The candidate is at or above Nginx's published 1.30.6 security fix level, but still needs selected platform digest and current package scan before build/rollout.

On the 4 GB / 2 vCPU production host, the **current** five-service caps total 2944 MiB / 1.70 vCPU under ADR-0024. A proposed 32 MiB / 0.1 vCPU Nginx would make a transitional six-service nominal sum 2976 MiB / 1.80 vCPU, leaving 1120 MiB / 0.20 vCPU by caps; this is a static estimate only, and the 32 MiB Nginx cap could be too tight with TLS, rate-limit zones and uploads. Dev watch caps are much higher and belong on the workstation. Do not deploy that six-service stack on the customer host from this arithmetic. Target full `db-local + fs` caps are 3040 MiB before OS/Docker, startup overlap and filesystem cache; measure host CPU/RSS, auth license lookup latency, DB connections (40 ceiling; planned app pools 30), disk and restore before accepting it. Do not add Redis/worker/inventory to the transitional gateway stack as a way to make the new names appear.

For later `db-local + fs`, preserve the PG18 data-parent mount behavior, introduce separate auth/master/inventory app and migration roles, and stage bind mounts and backup/restore before moving any named-volume data. Migrations run once, serially and backward compatibly before new app startup, not on every production image start. Storage ownership is by service prefix; Nginx gets read-only access only when protected delivery is implemented. Customer-owned off-server backup target, RPO/RTO acceptance and production TLS/hostname remain separate facts. Rollback for A returns browser traffic to the existing frontend port; B/C revert affected Nginx prefixes while old code and DB schema remain compatible. A post-write incompatible schema change needs a verified backup and recovery-point decision, never volume deletion.
