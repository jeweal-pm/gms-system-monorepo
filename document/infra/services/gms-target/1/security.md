### Nginx candidate, path contract and safe rollout

As of 2026-10-20, NGINX's [security advisories](https://nginx.org/en/security_advisories.html) list 1.30.6+ and 1.31.7+ as fixed for the October issues, and [Docker Hub's official unprivileged tag API](https://hub.docker.com/v2/repositories/nginxinc/nginx-unprivileged/tags/1.30.6-alpine3.24) reports the 1.30.6 Alpine 3.24 image above. Its [maintainer documentation](https://github.com/nginx/docker-nginx-unprivileged) specifies non-root operation, default port 8080, PID/temp paths in `/tmp`, and recommends digest pinning because tags are rebuilt. Prefer the stable 1.30.6 candidate over an older vulnerable pin; recheck image/base-package advisories and platform digest before implementation. This is version-specific **research**, not an image security attestation. Review this ingress research by **2026-11-20**, and immediately upon a new advisory, image rebuild, host/Engine/Compose change or changed TLS/route contract.

Use `8080` for HTTP inside the container and `8443` for TLS, with only host `80:8080` and `443:8443`; port 80 serves a bounded ACME challenge (if selected) and redirects otherwise. Configure a read-only root with only `/tmp` writable if `nginx -t` and runtime prove it, mount certificates/config read-only, give Nginx the selected fs storage read-only, use `init: true`, drop all capabilities and set `no-new-privileges` if the image passes those checks. The 32 MiB limit remains a **target** to test with TLS, rate-limit zones and upload concurrency, not an observed safe value. Do not use an image entrypoint template that tries to write under a read-only `/etc/nginx`; generate/bake validated config in CI or provide only the verified writable path. Resolve certificate renewal and reload permissions without Docker socket access.

The target precedence is exact upload routes and internal `/_storage/` first, then `/api/auth/`, `/api/master/`, `/api/inventory/`, immutable `/_next/static/`, permitted `/public/`, and finally `/` to frontend. Preserve the full URI prefix (`proxy_pass http://service:3000;` without a trailing URI slash), request body/Host/scheme/correlation headers, and cookie path/domain behavior. Explicitly deny external `/_storage/` and `/internal/`; `X-Accel-Redirect` may serve only a backend-authorized canonical file key from the read-only mount, with `nosniff`. Cache only immutable hashed static assets, not login, authenticated SSR, APIs, token refresh or file-authorizing responses. Restrict `real_ip` to the actual upstream proxy CIDRs; never trust an arbitrary incoming `X-Forwarded-For`. Put a bounded login rate limit on the **actual** Better Auth sign-in path after checking NAT behavior. Set finite body size and disable request buffering only for approved streaming-upload routes. [NGINX proxy URI semantics](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [real-IP module](https://nginx.org/en/docs/http/ngx_http_realip_module.html), [rate limiting](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html), [internal locations](https://nginx.org/en/docs/http/ngx_http_core_module.html).

For a nonproduction transition, first front the **existing** Next `/api/auth` and `/api/trpc` proxies through Nginx while retaining their upstream behavior. Test old login, logout, account/license activation and existing tRPC calls from the same origin before moving one approved prefix at a time to direct auth/master. Do not send `/api/auth/` directly to the new auth route until GP-AUTH code, cookies/CSRF and backend path base are verified. Keep the old gateway and proxies available for rollback until request logs show no callers and database/storage changes remain backward-compatible. Inventory, Redis/worker and Garage are not inserted into this first ingress slice. Never expose current `/internal/*` routes through the new proxy. Only Nginx gets host-published ports **after** an authorized cutover; current ports remain documented during the parallel staging period, so do not claim the target isolation already exists.

The customer-selected target Compose must map Nginx to private frontend/auth/master/inventory networks without granting Nginx DB/Redis access. Frontend SSR reaches domain APIs by Docker DNS; auth retains narrow outbound access to the license issuer. Domain APIs need key retrieval plus the **approved exception** for each protected online license decision; this path cannot be activated before GP-LIC-01. Network isolation must still permit managed DB/S3 egress in selected profiles. Passwords/keys/certificates require application-supported file readers or approved secret injection; merely adding Compose `secrets` does not change env-only app readers. Keep secret values out of `docker compose config` evidence. [Compose service controls](https://docs.docker.com/reference/compose-file/services/), [Compose secrets](https://docs.docker.com/reference/compose-file/secrets/).

## Current versus target boundary

The accepted stack is `frontend`, `backend-api-auth`, `backend-api-gateway`, `backend-api-partner`, `postgres`; current host-published ports are frontend 3000, gateway 4000, auth 3101, postgres 5432. Current production limits sum to **2944 MiB and 1.70 vCPU** under ADR-0024; actual production-image idle/load capacity is unmeasured. The target requires sole public Nginx 80/443, private frontend/auth/master/inventory/worker/Redis and optional local DB/Garage, no permanent Node gateway, domain-local JWT checks, new storage and queue contracts. Current named DB/photo volumes, root auth runtime and exposed ports are not the target profile. Do not layer target services on top of the existing five and call it migrated.

SA revision 1 now approves the *staged* transition from ADR-0007/0008/0016/0018/0024 and the narrow license exception; the central TODO still gates external license, selected inventory/storage/queue work and route cutover separately. Locally verified 15-minute JWTs alone do not preserve ADR-0016 next-request permission changes; the approved live view and online license design provide those checks only when implemented. Infra cannot solve this with network or Nginx settings. Existing partner ownership (including `stone` schema), files, and DB roles need an explicit data migration/rollback plan; service rename is not a data migration.

The [approved license offline design](../../../../spec/gms-license-offline-policy.md) checks remote status on each protected request and permits a configurable outage fallback (0–7 days, default 2) only from a still-valid signed eligible result. This creates auth-to-license-server egress on every protected request, plus a private domain-to-auth check, under the approved SA/spec exception. A remote revocation can remain unknown during outage grace; bound connection pools, timeouts and upstream request rate, and monitor fallback usage. The [proposed external contract revision 2](../../../../spec/gms-license-server-contract-rev2.md) is required because the current 24-hour signed token cannot support two-day fallback. No current mock client meets next-request online revocation.

## Target service and communication inventory

`web` means the private Nginx-to-app network; `data` and `queue` are private DB and Redis networks. These are proposed membership groups, **not per-port policy**. Internal Docker bridges do not establish service authorization. Only Nginx publishes host ports. Preserve application egress for the existing remote license service or selected S3/managed DB routes; Docker `internal: true` on every API network would break those calls. No container gets Docker socket, privileged mode, host PID/network, or host source-code mount in production.

| Caller -> callee | DNS/port/path | Auth/TLS and readiness | Network/egress boundary |
|---|---|---|---|
| Browser -> Nginx | customer host `:443` (`:80` redirect/ACME only) | valid TLS; one origin; trusted upstream proxy list for actual client IP | sole public ingress |
| Nginx -> frontend | `frontend:3000`, `/`, `/_next/static/`, `/bff/` | private HTTP; `/healthz`; forward Host, scheme, real client IP and `X-Request-Id` | `web`; no host publish |
| Nginx -> auth/master/inventory | `api-auth:3000` `/api/auth/`; `api-master:3000` `/api/master/`; `api-inventory:3000` `/api/inventory/` | private HTTP; `/readyz`; preserve prefixes and cookie/CSRF flow | `web`; no host publish |
| Frontend SSR -> APIs | service DNS `:3000` | forward validated user credential; never public-domain hairpin; no shared-user response cache | `web` |
| Domain APIs/worker -> auth key endpoint | `api-auth:3000` JWKS | pin issuer/audience/algorithms and bounded JWKS cache; reject unknown `kid`; exact key/refresh contract is SA-owned | `web`; no per-request auth call except explicit ADR exception |
| Auth/master/inventory/worker/migrations -> PostgreSQL | local `postgres:5432` or managed provider endpoint | own app/report/migration roles; `DB_SSL=off` local, `verify-full` with mounted CA managed; `/readyz` verifies DB | `data` or narrowly allowed provider egress; no host port |
| APIs/worker -> Redis | `redis:6379` | auth required; `/readyz` checks it; TLS only if selected topology crosses trusted local bridge | `queue`; no host port |
| Selected APIs/worker -> storage | `fs` bind mount or selected S3 endpoint | per-service key prefix, scoped S3 credentials; public presign host distinct from internal Garage endpoint | `fs` mount or controlled outbound network |
| Auth -> license issuer | exact existing `LICENSE_API_URL` contract TBD | existing signed-license validation and timeout/fail policy; must survive network partition | allow narrowly required external egress; never treat license JWT as user JWT |
| Backup operator -> backup target | customer NAS/off-server destination TBD | append-only push or NAS pull; production app containers do not receive delete-capable backup credentials | separate scheduled operational scope |

Nginx must pass `X-Request-Id`, original Host and trusted scheme consistently. Configure `real_ip` only for exact upstream load-balancer CIDRs; do not trust arbitrary browser `X-Forwarded-For`. Place login `limit_req` on the actual Better Auth sign-in route with a customer-approved rate/burst/status; validate legitimate NAT use. Stream upload bodies only on approved upload routes with a finite application-enforced byte cap; avoid globally disabling proxy buffering. `/_storage/` is `internal` with read-only fs mount, key validation upstream and `nosniff`; public files have their own controlled location. Cache only immutable `/_next/static/` content long-term, never authenticated SSR/API responses. Preserve WebSocket/upgrade only if a selected endpoint needs it. Nginx can listen internally on unprivileged 8080/8443 and map host 80/443, avoiding `CAP_NET_BIND_SERVICE`; prove the chosen image can read certs and write its temp/PID paths as non-root. [Nginx proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html), [real IP](https://nginx.org/en/docs/http/ngx_http_realip_module.html), [rate limit](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html), [internal/alias locations](https://nginx.org/en/docs/http/ngx_http_core_module.html).

|---|---|---|

| Frontend | standalone, non-root, read-only root if Next runtime permits; writable `/tmp` only if needed; no storage mount | 256 MiB, V8 160 MiB; `/healthz`; verify SSR burst and server cache bounds |

| api-inventory | same app isolation; streaming file work uses bounded disk-backed `/srv/gms/storage/.tmp`, never RAM tmpfs | 256 MiB, V8 192 MiB; `/readyz`; Hono runtime/image and API contract pending SA/backend |
| worker | same app isolation; only required DB, Redis, storage and S3 credentials; no public listener | 512 MiB / 1 vCPU, V8 384 MiB; fast concurrency 2, heavy 1, bounded pending jobs; readiness/termination contract pending |
| Redis | private network, authenticated, dedicated bind mount `/srv/gms/redis`, controlled UID/GID | 192 MiB container, `maxmemory 128mb`, `noeviction`, AOF; authenticated health probe must not print password |
| local PostgreSQL | private network, persistent `/srv/gms/postgres`, image-compatible UID/init; no blanket read-only root until entrypoint tested | 1024 MiB, `shm_size: 256mb`, 40 max connections, `pg_isready` is liveness only, app `/readyz` proves query readiness |
| Garage, only selected separately | private service, dedicated data/metadata/config bind mounts, per-bucket credentials and no host S3 port | 192 MiB **not viable with db-local on 4 GB** without approved measured redesign; v2.x license and exact image TBD |
| one-off migrations/backup jobs | separate scoped credentials, no public port; run sequentially | include peak overlap in host budget; never start them all with app stack automatically |

All runtime images: CI-built, pinned to digest after selection, multi-stage with production dependencies, `init: true` when compatible, non-root where possible, Docker default seccomp/LSM retained, capability drop and no-new-privileges tested per image, `pids`/CPU/RAM and `json-file` 10 MB x 5 logs. A read-only root needs explicit writable mount/tmpfs map per image; adding `read_only: true` blindly can break Nginx, PostgreSQL, Redis and Garage. Docker Compose file and secrets mechanism must match application file readers; Compose secret mounts do not automatically populate existing `DATABASE_URL`/`AUTH_SECRET` env variables. Use host files mode 0600 as interim only if approved and never expose values via `docker compose config` evidence. [Docker Compose service controls](https://docs.docker.com/reference/compose-file/services/), [secrets](https://docs.docker.com/reference/compose-file/secrets/), [production](https://docs.docker.com/compose/how-tos/production/), [environment caveat](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/).

## Database profiles and file profiles

### `db-local` (design default)

Use PostgreSQL >=16 with target tuning from spec section 3.3: `shared_buffers=256MB`, `effective_cache_size=768MB`, `work_mem=8MB`, `maintenance_work_mem=64MB`, `max_connections=40`, `max_parallel_workers_per_gather=1`, idle-in-transaction 60s and slow-log 500ms. Proposed pools 5 auth + 10 master + 10 inventory + 5 worker = 30, leaving 10 for admin/migrations; account for any report pools separately before implementation. The current image `postgres:18.6-alpine` uses the 18+ parent volume `/var/lib/postgresql` with PGDATA beneath it; 16/17 images use `/var/lib/postgresql/data`. Migration from existing `postgres-data` named volume to `/srv/gms/postgres` must be planned as backup/restore or verified copy with downtime, ownership, row counts and rollback. Existing initialization env vars/scripts do not rerun for populated data. Use separate `auth`, `master`, `inventory` schema owners/migration roles, app DML roles and report read-only role; reconcile existing `partner` and `stone` schemas before moving. Keep DB superuser out of app runtime. [Official Postgres image](https://hub.docker.com/_/postgres), [PG resource tuning](https://www.postgresql.org/docs/18/runtime-config-resource.html), [connection limits](https://www.postgresql.org/docs/18/runtime-config-connection.html).

### `db-managed` (separate customer choice)

Base Compose must have neither local Postgres nor unconditional `depends_on: postgres`; managed overlay mounts provider CA read-only into every DB consumer, including migration and worker. Require hostname-verifying TLS (`verify-full`) in driver configuration; prefer private provider network, otherwise restrict source IP. Confirm provider region/residency, PostgreSQL major >=16, extensions/collation, connection ceiling and transaction pooler behavior. Size all app/report/worker/migration connections with admin reserve. Provider PITR plus nightly independent per-schema `pg_dump -Fc` to the customer's off-server target; rehearse restore to db-local. App code remains the same across DB profiles. No managed provider has been selected.

### `fs` (design default)

Bind `/srv/gms/storage` to only the APIs/worker that need it as read-write and Nginx read-only. Use disk-backed `.tmp`; precreate directories with exact compatible UID/GID and quota/free-disk guard, do not recursively `chown` existing customer data without inventory. Separate `files`, `public`, `documents`, `exports` and service prefixes; backend package validates keys and access. Back up durable buckets, exclude exports/temp, keep document retention and soft-delete metadata in sync. Ensure backup account cannot delete historic copies.

### `s3-cloud` / `s3-garage` (separate customer choices)

Cloud S3/R2 requires residency/provider/egress consent, private least-privilege access keys, explicit CORS for browser uploads, per-bucket permissions and independent `rclone copy` of durable buckets. Internal SDK endpoint and public presign endpoint must be correct for signature host. Garage requires v2.x exact selected tag/digest, `replication_factor=1` with no redundancy, customer license review, private `garage:3900` and any public S3 route through Nginx only; include metadata/config backups and a restore drill. `db-local + s3-garage` is **not approved on 4 GB** by the spec: require >=8 GB or SA/owner-approved redesign backed by measurements. [Garage upstream deployment example](https://github.com/deuxfleurs-org/garage/blob/main-v2/doc/book/cookbook/real-world.md), [rclone copy semantics](https://rclone.org/commands/rclone_copy/).

## Redis, jobs, data recovery

Use an authenticated Redis instance with `requirepass` or an explicitly approved ACL credential design; protect 6379 by private network and no host publish. Set AOF and `maxmemory-policy noeviction`, `maxmemory 128mb`; AOF rewrites and copy-on-write can still exceed `maxmemory`, so verify RSS under 192 MiB and reserve disk. A `noeviction` write failure must surface as queue unavailable, not silently lose work. Queue growth is bounded by two pending/user, worker concurrency and TTL/retention; the producer and worker must have compatible Redis credentials and queue names. If Redis is introduced empty, no conversion is needed; for any existing Redis dataset, follow the upstream live AOF transition rather than only changing config. [Redis persistence](https://redis.io/docs/latest/management/persistence/), [security/authentication](https://redis.io/docs/latest/operate/oss_and_stack/management/security/), [noeviction behavior](https://redis.io/docs/latest/develop/reference/eviction/).

Proposed recovery targets pending customer agreement: database RPO <=15 minutes, files <=24 hours, RTO <=4 hours. Local DB: pgBackRest repository in `/srv/gms/backups/pgbackrest`, WAL archiving/PITR, weekly full and daily differential with two full retained; encrypted/append-only off-server copy or NAS pull. Managed DB: provider PITR plus independent schema dumps. Files/S3/Garage: copy durable data and Garage metadata/config where applicable; no `rclone sync` on backup target. Quarterly restore to a fresh server validates DB/file consistency and a working app. Alert on disk >80%, backup failure, queue wait/depth, uptime, memory/CPU and slow responses. Backup destination and credentials are customer-specific and remain unresolved. [pgBackRest backup/restore and archive guide](https://pgbackrest.org/user-guide.html).

## Capacity calculation and evidence gate

For **target db-local + fs**, target service hard memory limits are 1024 + 256 + 384 + 384 + 256 + 512 + 192 + 32 = **3040 MiB**. On a 4096 MiB host this leaves **1056 MiB** for OS/Docker, page cache, shared-memory accounting, temporary overlap and jobs. The spec's approximately 3.5 GB whole-host estimate is not measured in this repo. The only explicit target CPU cap is worker 1.0 vCPU; a complete merged CPU allocation for all containers plus OS must be designed and measured below 2 vCPU, with acceptable p95 latency. `db-managed + fs/s3-cloud` removes the 1024 MiB DB cap (2016 MiB app cap); `db-local + s3-garage` adds 192 MiB (3232 MiB cap, only 864 MiB nominal headroom) and is disallowed by spec. `db-managed + s3-garage` needs its own selected, measured budget. PostgreSQL 256 MiB shared memory is an allocation ceiling, not necessarily permanently resident; actual Docker/host usage must be checked. A 2 GB swap is an OOM safety net, never throughput capacity. Keep CI builds off the production host.

Before accepting a profile, collect actual production-host RAM/CPU/disk facts and production-image idle, cold-start, concurrent login, SSR, API and worker-load RSS/CPU/latency; include rolling update and sequential migration peak overlap, DB pool/connection counts, Redis AOF rewrite, upload/export disk, log growth and restore duration. Do not claim that static `mem_limit` addition proves fit. ADR-0024's five-service allocation remains current until a separately accepted migration supersedes it.

## Ordered transition, rollback and acceptance

1. SA records owner decisions: endpoint topology (domain tRPC vs temporary gateway), refresh and grant/license freshness, `partner`/`stone` data ownership, selected DB/file profiles, residency, recovery target and exact customer ingress. SA creates accepted revisioned ADR/contract/sequence/ER and includes this infra revision. No unreviewed traffic switch.
2. Backend/Frontend implement approved auth/access/CSRF, domain APIs, storage/queue adapters, migrations and health contracts with their own tests/reviews. Infra/DevOps then pin selected images/digests and prepare target Compose overlays, Nginx, secret readers, bind ownership and CI release path through the parent sole writer. Do not build on production.
3. Take and verify a restorable backup of the current named DB/photo volumes. Stage new bind mounts, roles and backward-compatible migrations. Run each one-off migration serially before new app startup, preserving old-version compatibility. For DB/file move, validate counts, checksums, document/file references and permissions before routing writes.
4. In an authorized staging or customer maintenance window, run merged Compose validation without printing secrets, Nginx config check, image provenance/advisory check, service readiness, host-port inventory (only 80/443), required paths and negative DB/Redis/API external-access checks. Exercise login/license/grant denial, CSRF, tRPC routes, upload and protected download, queue job, backup and fresh restore. Measure load and failure cases; record exact versions and timestamps.
5. Route traffic only after signed-off acceptance. Rollback means revert ingress to compatible old stack **only while database/storage schema and write compatibility are guaranteed**; otherwise stop writes and restore from verified backup with explicit recovery-point impact. Do not delete volumes or overwrite data to force rollback. Remove temporary gateway/ports only after the last dependent client is gone and audit evidence shows no use.
