## Domain and service boundaries

Auth remains the owner of Better Auth sessions, `auth.current_authorization`, immutable username/license subject resolution, signed v2 license validation and `auth.LicenseCurrentDecision`. Master remains the owner of customer/vendor domain procedures and `partner` tables during this staged migration. Master must not query auth base tables or receive signed license bytes.

Reuse the staged `LicenseService.resolveCurrentStatus(userId)` behavior and its ordered decision table. Add one private auth-owned `POST /internal/v1/license/current` contract for `backend-api-partner` to obtain a per-request decision. This is not a public API and does not alter the external license-server contract. The upstream license-server remains unimplemented in its separate repository; local and automated tests use the existing auth mock only. Do not claim production compatibility or perform production license-server work.

The two API processes require intended private service-to-service reachability. Proposed runtime path: a dedicated internal Compose network whose members are auth and the current partner/master process; it is not attached to Nginx and has no published port. Auth remains multihomed for its database and configured license-client paths; therefore Docker bridge membership is not a source-IP ACL and cannot prove only master can open TCP to auth. The **application credential is normative caller authorization on every interface**: the endpoint requires its dedicated token even when called over the intended private bridge. Do not claim bridge membership alone authenticates or isolates the caller. Nginx continues to route public `/api/master/trpc` through a separate web network and must reject `/internal/*`. The current auth host-port publication and Nginx-to-master network are outside this code contract and require the exact infra-reviewed topology before configuration changes. Do not remove ports, change Compose, or attach networks in this SA work.

Use a dedicated `MASTER_AUTH_SERVICE_TOKEN`, independent from `PARTNER_SERVICE_TOKEN`, CRM key, Better Auth secret and JWT keys. Generate 32 cryptographically random bytes, base64url-encode without padding (43 ASCII characters), and deliver only through an out-of-repository file-backed Compose secret mounted read-only at `/run/secrets/master_auth_service_token`, explicitly granted to auth and partner/master. Backend must implement a file reader using the non-secret path setting `MASTER_AUTH_SERVICE_TOKEN_FILE=/run/secrets/master_auth_service_token`; no environment value fallback is allowed. Reader accepts one 43-character base64url line, trims at most one terminal LF or CRLF, rejects all other whitespace/extra lines/missing/unreadable/incorrect-length data, stores only a digest, and compares in constant time. Never log the file contents. The host source file is outside repo/build context and readable only by the deployment operator. Windows/Docker Desktop file-mount behavior needs infra runtime verification before enabling the endpoint; no secret value is documented or stored. The route denies missing, malformed, duplicate or wrong authorization headers. No user/session identity is taken from arbitrary actor headers; the body contains only validated `userId` and `sessionId`, which auth resolves against its own live authorization view before calling license logic.

## Behavior and operation

The mounted master tRPC context sequence is: for a mutation, reject invalid CSRF evidence before JWT/JWKS, auth-view/license lookup or domain calls; then verify JWT signature/issuer/audience/expiry; read the live current-authorization row using the dedicated read-only DB role; verify row user/session match token and that account/session are active and session unexpired; call the private auth license endpoint; construct context; enter procedure permission middleware; only then invoke a customer/vendor domain service. No domain service is called after any failed gate. GET/HEAD/OPTIONS do not require the mutation CSRF check. On mutation, require exact trusted `Origin`, `X-GMS-CSRF: 1`, and `Sec-Fetch-Site` absent or `same-origin`/`same-site`, using only the configured trusted origin and Nginx-trusted forwarding policy. Keep the router's existing grant checks as defense in depth.

The auth endpoint independently validates its service credential, request schema, and exact live `(userId, sessionId)` row in `auth.current_authorization`; it also verifies the associated account is active and session is unexpired. It does not accept a username/license subject. `LicenseService.resolveCurrentStatus(userId)` resolves the immutable username in auth and performs the approved v2 check, with the already approved online denial/outage grace and ordered decision rules. Return no token or personal license subject.

Do not cache the private response in either service and do not retry it. Proposed auth endpoint deadline is 1,900 ms inclusive; its existing upstream v2 timeout is 1,500 ms. Master caller deadline is 2,000 ms, leaving 1,000 ms within the approved 3-second safe-read budget for JWT/JWKS and local DB work; if this cannot be met in measurements, return fail-closed 503 and require a revised capacity/timeout proposal rather than widening deadlines silently. A license-service error or network/DB timeout maps to unavailable, never eligible. Preserve `LICENSE_OFFLINE_GRACE_DAYS` 0–2, default 2, explicit-denial precedence and fixed signed-token fallback from ADR-0026/0028.

## Capacity and rollout

No container or library is added. Keep current service caps as ceilings (auth 512 MiB / 0.30 vCPU; partner 384 MiB / 0.25 vCPU; current aggregate 1.70 vCPU / 2944 MiB across the current stack). Keep pools bounded: auth <=5, partner <=5. The private call adds one bounded auth DB view read plus existing license sequence/write/read work and an upstream wait; do not hold a DB transaction/connection across the network wait. Measure p95/end-to-end latency, auth/partner RSS and DB connection use before route activation on the 4 GB RAM / 2 vCPU host. Do not claim target capacity based on static caps.

Roll out behind a disabled/unmounted route first. Apply additive grants/role provisioning before deploying master credentials; enable endpoint behind internal network; test auth service identity and view-only privilege boundaries; mount tRPC only after end-to-end HTTP tests and rollback checks. Rollback unmounts `/api/master/trpc` and returns browser traffic to the existing Next/gateway `/api/trpc` route. Keep auth v1 and v2 decision data additive; never delete or rewrite user/license data. No service rename or deployment is approved by this bundle.
