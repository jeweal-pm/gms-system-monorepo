## Verified current behaviour (code read 2026-11-07)

- All seven documents are created `PENDING_APPROVAL` and are editable/deletable only in `PENDING_APPROVAL` (`editableStatuses: [PENDING]` in `customer-stock-document.ts`, `memo-receive.service.ts`, `memo-return.service.ts`, `memo-out-return.service.ts`, `purchase-order.service.ts`, `purchase.service.ts`). Approve is a guarded `updateMany` on `{id, version, status: PENDING, deletedAt: null}` per service, with `explainMiss` (NOT_FOUND → DELETED → STATUS_INVALID → CHANGED).
- Status CHECKs are `IN ('PENDING_APPROVAL','APPROVED')`; `<t>_approved_check` ties `APPROVED` to `approved_at/by`; `<t>_deleted_check` allows a deleted row only in `PENDING_APPROVAL` (migration `20261106090000_transaction_soft_delete`).
- **Stock moves only inside `approve()`**: Reserve/Memo Out `takeFromMemoStock`, Memo Receive writes `memo_stock`, Memo Return reduces pending, Memo Out Return adds `returned_*`, Purchase `takeForPurchase` + `writeSoldParts`, PO writes nothing. Save of Purchase/Reserve/Memo Out/Memo Return only *checks* availability (`completeSourceLines`, `completeFromMemoStock`). Every reader (pickers, `memoStock.list`, `memoOutReturn.outstanding`, `memoOutstanding.*`, Purchase Outstanding, `purchase.purchaseOrderLines`) filters `status = 'APPROVED'` or reads `memo_stock` rows written by approval. A pending document can reference only APPROVED sources, and nothing references a pending document.
- Master stores user ids only (`created_by`, `updated_by`, `approved_by`, `deleted_by`). The master auth reader (`authz-database.ts`) may select only `auth.current_authorization`, which by design has no name (`backend-api-auth` migration `20261021090000…`). Auth `User` has `name` and `role` (`admin` | `user`) and **no position/department field**.
- The list order is `doc_date desc, created_at desc, id desc`; the list has no `version`, line count, stones, totals or submitter, and there is no aggregated count.

## SA defaults (owner may change)

| ID | Default | Why |
|---|---|---|
| D1 | **Status model** for the seven documents: `PENDING_APPROVAL` → `APPROVED` (approve, unchanged); `PENDING_APPROVAL` → `REJECTED` (reject, **final**); `PENDING_APPROVAL` → `REVISION_REQUESTED` (revise, shown as "Revise" / "Sent back"); `REVISION_REQUESTED` → `PENDING_APPROVAL` (resubmit). No other transition. Reject/Revise/Approve are allowed only from `PENDING_APPROVAL`. | Owner Q-AP-01/02. Reusing `REJECTED` matches Quotation's existing value. A separate status (instead of a flag) keeps "is it waiting for approval" a single indexed predicate. |
| D2 | Status CHECK becomes `IN ('PENDING_APPROVAL','APPROVED','REJECTED','REVISION_REQUESTED')` (18 chars, fits `VARCHAR(20)`). `<t>_approved_check` is unchanged (only APPROVED has `approved_*`). The list `status` filter accepts the four values. | The database backs the model, as for approve and delete. |
| D3 | **Reason / note storage**: header columns `review_action` (`REJECT` \| `REVISE`), `review_note VARCHAR(500)`, `reviewed_at`, `reviewed_by`, `reviewed_by_name`. Reject input `reason`, Revise input `note`, both trimmed 1–500 characters (same rule as `quotation.reject`). CHECK: all five null, or action + non-blank note + at + by set; `REJECTED` ⇒ action `REJECT`; `REVISION_REQUESTED` ⇒ action `REVISE`; action `REJECT` ⇒ status `REJECTED`. The **latest** review is kept: after a resubmit (and after a later approve) the last Revise note stays readable ("Previously sent back"); a new Revise overwrites it. History of earlier rounds is in the structured logs only (OQ-AP-4). | Who/when/why on the row itself, same pattern as `approved_*` and `deleted_*` (ADR-0045 D13). No audit table exists. |
| D4 | **Submitted**: new `submitted_at TIMESTAMP(3) NOT NULL`, `submitted_by VARCHAR(64) NOT NULL`, `submitted_by_name VARCHAR(200) NULL`. Set on create and on resubmit; an edit while already pending does **not** change it (OQ-AP-8). Backfill: `created_at` / `created_by`; name NULL for existing rows (shown "—"). | Q-AP-14 default "the save that put it in Pending". Approve Center sorts and shows by it. |
| D5 | **Names without a cross-service lookup**: auth appends one column `user_name` (the session owner's `User.name`) to the `auth.current_authorization` view (auth-owned migration; the reader grant is unchanged). The master auth context exposes it as `principal.displayName`. Master **snapshots** the actor's own name (trimmed, ≤ 200 chars, null if missing) into `submitted_by_name` / `reviewed_by_name` when it writes those columns. Master never reads other users' names. | No per-row fan-out, no new endpoint, pool or cache; the view is already read on every request. A snapshot matches how documents keep party names. Amends ADR-0031 item 5 for one column (ADR-0046). Alternatives in the ADR; OQ-AP-2. |
| D6 | **Role**: auth has only `admin` / `user`, so the "(Sales)" part of the design has no source. The API returns no role; the UI shows the name only ("Mint", not "Mint (Sales)"). | Do not invent data. A Position field would be a separate User & Permission feature (OQ-AP-1). |
| D7 | **Editability**: editable statuses become `PENDING_APPROVAL` **and** `REVISION_REQUESTED` (update and soft delete). `REVISION_REQUESTED` documents are **not** listed in Approve (pending only) and cannot be approved; after `resubmit` they return to Pending with a new `submitted_at`, so they go to the end of the oldest-first queue (OQ-AP-5). Resubmit needs the `<menu>` EDIT grant; any EDIT user may edit and resubmit, as any EDIT user may edit a pending document today (OQ-AP-3). Resubmit does not re-validate content; the edit before it does (the normal save rules), and Approve re-checks stock under lock as today. | Smallest change to the engine: Revise behaves like "pending, but not approvable". |
| D8 | **Soft delete (ADR-0045)**: deletable = `PENDING_APPROVAL` and `REVISION_REQUESTED`. `APPROVED` and `REJECTED` cannot be deleted; `<t>_deleted_check` is replaced accordingly. Restore returns the document to the same status. Reject, Revise and Resubmit on a deleted document → `<CODE>_DELETED`. | Rejected is final and kept as a record (OQ-AP-6). |
| D9 | **Stock: none.** Reject, Revise and Resubmit change no `memo_stock`, `purchase_order_line.purchased_*`, `memo_out_line.returned_*` or counter. Stock IDs already issued at save (Memo Receive, Purchase MANUAL/PO lines) stay on the document's lines and are never reissued (as ADR-0045 D17). | Verified above: stock moves only in approve; readers use APPROVED only; a rejected/revised document is never APPROVED. |
| D10 | **Purchase / PO specifics**: `purchase.get` returns `limit*` / `min*` while the purchase is **editable** (`PENDING_APPROVAL` or `REVISION_REQUESTED`), not only `PENDING_APPROVAL`. A rejected Purchase keeps its `memo_stock_id` / `purchase_order_line_id` links (FK RESTRICT, harmless; nothing is cut). A PO can only feed a Purchase once APPROVED, so a pending PO is never referenced and Reject/Revise of a PO is always safe; Purchase Outstanding is unchanged. Memo Out Return: a rejected return changes no Memo Out line. | Verified in `purchase.service.ts` (`get`), `purchase-stock.ts`, `purchase-pickers.ts`. |
| D11 | **Permissions**: `reject` / `requestRevision` = `<menu>` APPROVE + CSRF; `resubmit` = `<menu>` EDIT + CSRF; `approval.pending({type})` = `<menu>` APPROVE **and** VIEW; `approval.summary` = live session, then filtered to types with APPROVE and VIEW (Super Admin: all). The creator may approve/reject/revise their own document (Q-AP-16, as today). No new action, so the auth permission catalog is unchanged. | Owner Q-AP-13. Reuses the existing grant middleware. |
| D12 | **Errors**: no new domain codes for the document procedures; reuse `<CODE>_NOT_FOUND` 404, `_DELETED` / `_STATUS_INVALID` / `_CHANGED` 409, `VALIDATION_ERROR` (`reason` / `note`), `PARTNER_UNAVAILABLE` 503. `approval.*`: `VALIDATION_ERROR` (`type`, `cursor`, `q`, `sort`), `PERMISSION_DENIED`, `PARTNER_UNAVAILABLE`. | Clients already map these ([error-handling](error-handling.md)). |
| D13 | **Audit**: structured logs `<event>.rejected`, `<event>.revision_requested`, `<event>.resubmitted` with `{actorId, id, docNo, version, noteLength}`; the note text is **not** logged. | Business text stays in the database; logs stay small. |
| D14 | **Approve Center API** lives in `backend-api-master` (all seven documents are there) as a new read-only `approval` router with `summary` and `pending`. Approve, Reject and Revise are the **per-document** procedures (`<doc>.approve`, new `<doc>.reject`, `<doc>.requestRevision`), so each keeps its own grant, guard and stock logic. Bulk approve stays sequential on the client. | Reuse; no "approve anything" endpoint that would bypass per-menu rules. |
| D15 | **`approval.summary`**: one SQL statement, `UNION ALL` of one capped count per permitted type: `count(*) FROM (SELECT 1 … WHERE status='PENDING_APPROVAL' AND deleted_at IS NULL LIMIT 100)`. A count of 100 means "100 or more" (the UI shows `99+` above 99). Types without APPROVE+VIEW are omitted. No server cache; the client caches 60 s, refetches on focus and after approve/reject/revise; **no polling, no push**. | One query per call, each bounded by the partial index (D18). |
| D16 | **`approval.pending`**: one type per call; rows with `version`, party, ref, value, line count, Σ pcs, Σ weight, up to 3 distinct stone names in line order + the remainder count, submitted time/by/name, last Revise (if resubmitted). Sort `submittedAt` (default, **ascending** = oldest first), `docNo`, `party`, `qty` (Σ weight), `value` (currency, then grand total); `dir` asc/desc; keyset cursor bound to the sort and search; limit 1–50 (default 50); no `total` (use `summary`). `q` (trimmed ≤ 100, LIKE-escaped) matches doc no., party name, ref, **line stone name and line Stock ID** (Memo Out Return via its Memo Out line). | Q-AP-11/15. One bounded statement per page. |
| D17 | **Header totals**: new `line_count SMALLINT`, `total_pcs INTEGER`, `total_weight_ct DECIMAL(15,3)`, all `NOT NULL`, written by the engine on every create/update from the stored lines (Memo Out Return: the Return quantity), backfilled from the lines. | Qty sort and display without aggregating lines across all pending documents. |
| D18 | **Indexes**: per table one partial index `<t>_pending_idx (submitted_at, id) WHERE status='PENDING_APPROVAL' AND deleted_at IS NULL`. It serves the counts and the default sort (both directions). Other sorts and line search sort/scan only the pending set of one type. Existing indexes stay. Add per-sort partial indexes only if M-AP-01 shows a type above 2 000 pending or `pending` p95 above 150 ms. | Pending sets are small working queues; 7 small indexes. |
| D19 | **Quotation** is unchanged: not in `summary` / `pending`, "off" in the UI permanently; its existing `reject` / `REJECTED` / `statusReason` stay as they are. | Owner Q-AP-06. |
