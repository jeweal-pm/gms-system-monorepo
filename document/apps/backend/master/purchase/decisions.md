## Decisions

| ID | Decision |
|---|---|
| SA-PU-01 | **Tables** (migration `20261104150000_purchase`, additive): `purchase`, `purchase_line` and `purchase_charge` in schema `partner`. The header and charges are shaped like `purchase_order` / `memo_receive`: vendor plus one address snapshot (ADR-0019 §4), currency, exchange rate, server totals, `approved_at/by` and `version`. The same migration adds to `memo_stock`: `purchased_pcs` int and `purchased_weight_ct` numeric(12,3), both default 0, with CHECK `memo_stock_purchased_check` (0 ≤ purchased ≤ sold, for pcs and weight). It also adds two partial indexes: `memo_stock_sold_open_idx` and `purchase_order_line_open_idx`. See the [database diagram](database-diagram.md). |
| SA-PU-02 | **Engine:** `PurchaseService` (`src/purchase/`) uses `TradeDocumentEngine` with the vendor party adapter (shared with Memo Receive, Memo Return and Purchase Order). Settings: `document: "purchase"`, `transactionKey: "purchase"`, `createStatus: PENDING_APPROVAL`, `editableStatuses: [PENDING_APPROVAL]`, no `lineOmit`. The `prepare` hook completes source lines and checks availability (SA-PU-07). A line hook writes `memo_stock_id`, `memo_group`, `purchase_order_line_id`, `stock_id` and the copied `stone_code_id`, and keeps the ids of saved lines. Engine `delete` is reused unchanged, because a pending purchase holds no stock. `approve` is written in `PurchaseService`, as the Memo Return approve is. |
| SA-PU-03 | **Line sources** (`purchase_line.source`):<br>• `STOCK` = a Memo Stock item, from the Memo Stock button. It needs `memoStockId` and `memoGroup` (`IN_STOCK` or `SOLD`).<br>• `PURCHASE_ORDER` = an approved PO line, from the Purchase Order button. It needs `purchaseOrderLineId`.<br>• `MANUAL` = keyed in (Q-PU-05).<br>For `STOCK` and `PURCHASE_ORDER` lines the server ignores the copied fields the browser sends and fills them from the database row: stone code (PO only), stone, shape, size, color, clarity, cutting, quality, lot, location, cer type, cer no and price unit. For a STOCK line the Stock ID is the item's; for a PO line it is issued (SA-PU-10). The user edits **pcs, weight and unit price**, plus the item note (UI rev 2 R2-03, R2-D-07). The **line discount is locked**: a source line must send `discount {type: "NONE"}`, otherwise `VALIDATION_ERROR lines.N.discount` / `not_allowed`. Every other copied field is overwritten from the source, so a picked line can differ from its source only in pcs, weight, price and note. Each line needs pcs > 0 or weight > 0, and a unit price > 0 (Q-PU-04). A Memo Stock item may appear at most once per group in a document, and a PO line at most once per document. |
| SA-PU-04 | **Timing (SA default D2): Save checks, Approve cuts.** `create` and `update` give or keep `PENDING_APPROVAL` (Q-PU-06 default). They check each source quantity against its current availability without a lock, and change no stock. `approve` moves all the quantities in one transaction, under row locks, with the over-pull guard. Two pending purchases may name the same quantity, and only the first approval succeeds (the Q-MR-15 guard). Edit and delete of a pending purchase touch no stock. An approved purchase is read-only and there is no un-approve, so nothing ever gives stock back. |
| SA-PU-05 | **Memo Stock effect at Approve** (the existing bucket plus a settlement counter):<br>• `IN_STOCK` line (bought out of pending): `pending −= q`, `sold += q`, `purchased += q`. The guard is q ≤ pending.<br>• `SOLD` line (a stone already sold to a customer, now bought from the vendor): `purchased += q`, and nothing else changes. The guard is q ≤ sold − purchased.<br>`memo_stock_balance` (pending = received − returned − sold − reserved) is **unchanged** and still holds. `sold` keeps its owner-approved meaning (Q-MOV-04: the design's "PO/Purchase" column is Sold): the quantity that left the memo by sale, to a customer or to us. `purchased` (≤ sold) records how much of that the vendor has already been paid for, so "sold − purchased" is "sold to customers, must be purchased". **Memo Outstanding › Vendor needs no code change.** Approved purchases appear in its Sold column and leave Outstanding, Return + Sold + Reserve + Outstanding = Memo still holds, and a fully bought item drops off the report through the existing open filter. `memo_stock.version` + 1 on every change. |
| SA-PU-06 | **Purchase Order effect at Approve** (owner clarification; SA-PO-05): a `PURCHASE_ORDER` line adds its pcs and weight to `purchase_order_line.purchased_pcs` / `purchased_weight_ct`. The guards are pcs ≤ `pcs − purchased_pcs` and weight ≤ `weight_ct − purchased_weight_ct`, backed by the existing CHECK `purchase_order_line_purchased_check`. The PO must be `APPROVED` and have the purchase's vendor and currency, checked at Save and again at Approve, otherwise `PURCHASE_REFERENCE_INVALID` at `lines.N.purchaseOrderLineId`. An approved PO cannot be edited or deleted (SA-PO-03), so its status needs no lock. The PO header is never written. |
| SA-PU-07 | **Save** (engine `WRITE_TX`): `prepare` reads the source rows by primary key, without a lock, and checks vendor, currency, PO status and the duplicate rules. It copies the source fields and refuses a quantity above the current availability with `VALIDATION_ERROR lines.N.pcs|weightCt` / `exceeds_available`, the way Memo Return refuses `exceeds_outstanding` at save. It moves no stock. Then the engine runs as usual: number under the numbering lock, line hook (Stock IDs, counter lock) and the header, lines and charges. Update replaces lines and charges under the engine's status and version guard. The browser's pending, available, price-unit and stone fields are never trusted (security note, 2026-11-04). |
| SA-PU-08 | **Delete** (`purchase:DELETE`): the engine `delete`. `PENDING_APPROVAL` only, guarded by version, with lines and charges CASCADE. No stock change, because nothing was cut. The next save may reuse the latest number (Q-QT-03 rule). Issued Stock IDs are not reused. |
| SA-PU-09 | **Approve** (`purchase:APPROVE`; the creator may approve), one `WRITE_TX` (4 s / maxWait 2 s):<br>1. A guarded `UPDATE purchase SET status = 'APPROVED', approved_at, approved_by, version + 1 WHERE id AND version AND status = 'PENDING_APPROVAL'`. Zero rows → re-read for NOT_FOUND / STATUS_INVALID / CHANGED. This also serializes approvals of one document.<br>2. Read the lines, summed per key (memo stock item × group, PO line; `totalPerItem`, INV-20261031-001).<br>3. Lock the touched `memo_stock` rows `FOR UPDATE` in id order, then the touched `purchase_order_line` rows in id order, and re-check that each PO is still APPROVED with the same vendor and currency.<br>4. Guard every key against the locked values. If any key is short, throw `PURCHASE_PENDING_SHORT` (409) with fieldErrors `lines.N.pcs|weightCt` / `exceeds_available` for every short line. The whole transaction rolls back and the document stays pending.<br>5. Apply each table's changes in one `UPDATE … FROM (VALUES …)` (the `takeFromMemoStock` pattern).<br>Manual lines move nothing, so a purchase with only manual lines approves with no stock change. Lock order: purchase → memo_stock → purchase_order_line. The other memo_stock writers lock only memo_stock, in id order, so there is no deadlock. Log `purchase.approved` (id, docNo, line count, memo stock keys, PO keys). |
| SA-PU-10 | **Manual rows and Stock IDs** (Q-PU-05 default, approved; SA picks the timing): `MANUAL` and `PURCHASE_ORDER` lines get a Stock ID **at Save** from the shared `memo_stock_id_counter` (`YY####`, the Bangkok year of the save, `issueStockIds`, SA-MR-04, the Memo Receive pattern). The id is kept on update when the line sends its saved `id`. Running out → `PURCHASE_STOCK_ID_EXHAUSTED` (409). `STOCK` lines keep the item's Stock ID. Issued ids are unique (partial unique index). Manual lines: an optional Stone Code from Stone Master (active, or the one already stored), the seven stone fields, quality, lot, a **free-text Location ≤ 40** (as PO, Q-PO-06; blank shows "—", D10), cer type and no, price unit, pcs, weight, price, line discount and note. A manual line moves no stock. |
| SA-PU-11 | **Header, totals and number:** the SA-PO-07 rules. Active vendor plus one of its addresses (or the stored ones), snapshots; currency active or stored; exchange rate required for a foreign currency, read-only in the UI (Q-PU-13); due date ≥ doc date (Q-PU-10, payment due); ref ≤ 100; note ≤ 500 (the UI caps it at 250); server totals with the quotation calculator and the SA-MR-09 discount bounds. Number: Document Setup key `purchase` (exists, code `PU`, Q-PU-07). `NumberedDocument` gains `purchase` (advisory key `partner.purchase.plain_running_no`). Document Setup `used` also counts `purchase`. `nextNumber` gives a preview. |
| SA-PU-12 | **Memo Stock picker**, `purchase.memoStock` (new query, `purchase:VIEW`). It lists the vendor's items in the document currency as rows of two groups:<br>• **SOLD**, "Sold to customers · must be purchased": available = `sold − purchased` > 0.<br>• **IN_STOCK**, "Still in stock on memo": available = `pending` > 0.<br>A partly sold item is **one row per status**, with its own quantity, cap and amount (Q-PU-16). Rows come with a `status` filter, Sold-first order, tab counts `{all, sold, inStock}` for the current search and dates, search over Stock ID, lot, stone, cer no and memo no (plus invoice no once a Sale exists), and a date range on the Memo Receive Doc Date (≤ 366 days).<br>**Q-PU-16, where "sold to customers" comes from today: nowhere.** No Sale / invoice table or service exists, and nothing writes `memo_stock.sold_*` today (memo-outstanding-customer SA-MOC-02: "Sold = 0 until Sale"). Memo Out Return has no "sold" decision either: it only moves Reserve back to pending (SA-MOR-17). Approved Memo Outs keep the stones in Reserve, which is a loan, not a sale. So nothing can be derived. In revision 1 the SOLD group is always empty and the Sold tab count is 0. Each row's `sale` (invoice no, invoice date, customer name) is `null`, and **no invoice is invented**. The later Sale revision writes `sold_*` and supplies `sale`.<br>The piece type (Pair / Parcel / Single, R2-D-04) is `null` because no such field exists, and `location` is the real column, which is always "Memo" today (Q-PU-19 default).<br>Everything else in the dialog has data (see the [api-contract](api-contract.md#memo-stock-picker)). Reserved quantities (out with a customer on memo, or held) appear in neither group (D5).<br>This is a Purchase-specific query. `memoStock.list` is **not** changed and **not** re-granted, so Memo Return, Memo Out, Reserve and Quotation keep their contract (Q-PU-23). |
| SA-PU-13 | **Purchase Order picker**, `purchase.purchaseOrderLines` (new query, `purchase:VIEW`). It lists lines of `APPROVED` POs of the vendor in the document currency with outstanding pcs or weight > 0 (`pcs − purchased_pcs`, `weight_ct − purchased_weight_ct`). A `status` filter and counts cover the tabs All / Open / Partly purchased (UI rev 2 Q-PU-20). OPEN means nothing has been purchased yet; PARTLY_PURCHASED means purchased > 0 and something is still outstanding. Search covers PO no, stone, lot and cer no; a date range on the PO Doc Date (≤ 366 days). Keyset ≤ 50, newest PO first, then line position, so lines of one PO stay together for the group rows. Each row gives the PO header (id, doc no, doc date, due date, ref), the line's stone fields, the ordered, purchased and available quantities, the price unit, the unit price and the net unit price after the line discount (2 dp, used as the starting Price, D12). This replaces the Q-PU-02 "disabled" default by the owner's 2026-11-04 instruction. |
| SA-PU-14 | **Server trust:** the input carries only ids, the source group, pcs, weight, price, discount and note for source lines. Availability, Stock ID, stone fields and price unit are always read from the database: at Save without a lock, at Approve under the lock. Totals are recomputed by the server. A Memo Stock item of another vendor or currency, a PO line of another vendor or currency, or a PO that is not approved → `PURCHASE_REFERENCE_INVALID` with the line path. |
| SA-PU-15 | **Permissions:** catalog leaf `purchase` (exists, ADR-0020); `MasterMenu` gains `"purchase"`. VIEW = list, get, options, nextNumber, memoStock, purchaseOrderLines, and `currency.options` (added to its any-of list). ADD = create. EDIT = update. DELETE = delete. APPROVE = approve. Mutations need CSRF. `purchase.get` checks `purchase:VIEW` (security note). No auth migration and no catalog change. See [authorization](authorization.md). |
| SA-PU-16 | **List and get:** `purchase.list` is the engine keyset `(doc_date desc, created_at desc, id desc)`, ≤ 50 rows, with filters status, vendor and date range (≤ 366 days) and a search on doc no, vendor name and ref (≤ 100 characters, escaped). The daybook uses this list. `purchase.get` returns the document. For a `PENDING_APPROVAL` document each source line also gets `limitPcs` / `limitWeightCt` = the source's current availability, read in ≤ 2 bounded primary-key queries. Those are the row maximum while editing. They are `null` for approved documents and manual lines. |
| SA-PU-17 | **Errors and audit:** `PURCHASE_NOT_FOUND` 404, `_CHANGED` 409, `_STATUS_INVALID` 409, `_REFERENCE_INVALID` 422 (field named), `_PENDING_SHORT` 409 (approve, line fields), `_STOCK_ID_EXHAUSTED` 409, plus the shared `VALIDATION_ERROR` (including `exceeds_available` at save), `PERMISSION_DENIED`, `CSRF_INVALID`, `UNAUTHORIZED`, `AUTHORIZATION_UNAVAILABLE` and `PARTNER_UNAVAILABLE`. Logs `purchase.created/updated/deleted/approved` hold only ids, doc no, line counts and the number of memo stock / PO keys moved. They never hold prices, vendor names or quantities. See [error-handling](error-handling.md). |
| SA-PU-18 | **Own stock (คลัง Pmr), Q-PU-03 part 2: deferred** to the inventory service (ADR-0027 boundary; not built). No interim table and no new container. The approved purchase lines keep source, memo stock id, PO line id, Stock ID, pcs, weight, price unit and unit price, so a later inventory revision can backfill own stock from them. **Known gap (D4):** bought stones can no longer be picked as From Stock on Memo Out, Reserve or Quotation: approved STOCK lines leave pending, and MANUAL / PO lines are recorded on the document only. |
| SA-PU-19 | **Photos and Duplicate:** photo ids must be an empty array (Q-PU-11, `max(0)` as on memo documents). No storage module, nginx location or `@gms/storage` scope in this revision. Duplicate (Q-PU-08) copies every row on the client. The new save re-checks current availability, and its approval re-checks under the lock. |
| SA-PU-20 | **Not in this revision:** un-approve, reject or cancel; the Purchase Outstanding report; payable or vendor-invoice posting; own stock / inventory; a Sale document (the SOLD writer); purchasing Reserved quantity; line photos; print / Excel; PRICE masking. |

## SA defaults (owner may change)

Each item below is a decision SA made where the owner's 2026-11-04 rules are silent. Each is the most conservative option that fits the existing patterns. Changing one is a new SA revision.

| # | SA default | Alternative the owner may prefer | Effect of changing |
|---|---|---|---|
| D1 | **Bucket:** existing `sold` plus a new `purchased` counter (≤ sold). No change to `memo_stock_balance` or to Memo Outstanding › Vendor. `sold` means "left the memo by sale", to a customer or to us. "Sold to customers, must be purchased" is `sold − purchased`, so the two meanings never collide (the ui-spec Q-PU-03 rev 2 concern). | The ui-spec recommendation: a separate **Purchased** bucket where `sold` is customer-only. Purchasing a sold row moves sold → purchased, the CHECK becomes pending = received − returned − sold − reserved − purchased, and the report gets a Purchased column (or Sold shows sold + purchased). | CHECK change, report SQL and UI change (the Q-MOV-02 identity changes). |
| D2 | **Timing: cut at Approve, check at Save** (Q-MR-15, as Memo Return / Memo Out / Reserve). A pending purchase holds nothing. Two pending purchases can name the same quantity; the first approval wins and the second gets `PURCHASE_PENDING_SHORT`. | **Cut at Save** (a pending purchase holds its quantity). Update would give back and re-take under locks, and delete would give back. | A hold/release design in save, update and delete. The vendor report would then show pending purchases in Sold. |
| D3 | **Approval kept** (Q-PU-06 default): Save → Pending Approval, Approve → stock cut and read-only. | No approval: Save is final and cuts stock at once. | `approve` removed; save takes the locks. |

| D6 | The **SOLD group is empty** until a Sale document exists. Invoice no / date / customer and the Location type (Pair/Parcel/Single) are `null`. | Treat approved Memo Out (stones with customers) as "sold". | That would mislabel memo loans as sales. It is not recommended. |
| D7 | Stock IDs for MANUAL / PO lines are issued **at Save** from the shared `YY####` counter (Memo Receive pattern). A deleted purchase leaves a gap. | Issue at Approve. | Fewer gaps, but the row shows "Auto" until approved. |
| D8 | On picked (source) lines only **pcs, weight, price and item note** are editable. The line discount is locked to NONE (UI rev 2 R2-03). Manual lines keep the line discount. | D13 | Picker **date range** filters the Memo Receive Doc Date (memo) or the PO Doc Date (PO), ≤ 366 days. The design's "Start → Due" label is shown, not filtered on due date. | Filter on due date. | Query change only. |

Capacity: a save writes ≤ 200 lines and 4 charge rows and reads its sources by primary key. Approve locks and updates at most 200 `memo_stock` rows and 200 `purchase_order_line` rows in two statements. Lists and pickers are keyset ≤ 50, each with one bounded count. There is no new container, pool, cache or job, so the ADR-0024 4 GB / 2 vCPU budget is unchanged (api-master 0.25 vCPU / 384 MiB).

## SA revision 2 (proposed 2026-11-05): merged Memo Stock lines

- Status: **pending-review** 2026-11-05. Approval evidence: none. Source UI: [ui-spec › Revision 3](../../../frontend/purchase/ui-spec.md#revision-3-merge-the-sold-and-in-stock-parts-of-one-item-pending-review); questions Q-PU-24…35.
- ADR: [ADR-0043](../../../../adr/0043-purchase-merged-memo-stock-line.md) (Proposed). Builds on SA rev 1 and ADR-0042 without changing D1 (bucket) or D2 (cut at Approve).
- Service `backend-api-master`, schema `partner`. No new service, container, route, cache or package.

| ID | Decision |
|---|---|
| SA-PU-21 | **New memo group `MERGED`** for a `STOCK` line: one `purchase_line` that buys the Sold part and the In-stock part of **one** Memo Stock item (Q-PU-24). `memoGroup` becomes `IN_STOCK` \| `SOLD` \| `MERGED`. On one purchase, an item is either one `MERGED` line or at most one `SOLD` and one `IN_STOCK` line, never both forms: otherwise `VALIDATION_ERROR lines.N.memoStockId` / `duplicate`. |
| SA-PU-22 | **Save rule for MERGED** (no lock, as SA-PU-07): with `soldOpen = sold − purchased` and `pending` of the item, each of pcs and weight on its own must satisfy `soldOpen ≤ q ≤ soldOpen + pending` (Q-PU-31). Below → `VALIDATION_ERROR lines.N.pcs|weightCt` / `below_sold`; above → `exceeds_available`. `soldOpen` must be > 0 in pcs or weight and `pending` > 0 in pcs or weight, else `not_mergeable` (there is nothing to merge). Price > 0; line discount NONE (D8). |
