- Service: `backend-api-master`, schema `partner`. It reads `memo_receive` + `memo_stock` (memo-receive SA rev 1–2). No new service, container, route or package.

| ID | Decision |
|---|---|
| SA-MOV-01 | Read-only tRPC router `memoOutstanding` with `vendorSummary`, `vendorList`, `vendorItems` and `vendorOptions`. Nothing is written. |
| SA-MOV-02 | **Bucket counters on `memo_stock`** (additive migration `20261030090000_memo_stock_buckets`): `returned_pcs/_weight_ct`, `sold_pcs/_weight_ct`, `reserved_pcs/_weight_ct`, default 0, CHECK ≥ 0. A table CHECK enforces `pending = received − returned − sold − reserved` for pcs and weight. Existing rows backfill to 0 and stay valid. Later approvals (Memo Return, Sale/Purchase, Reserve/Memo Out; Q-MR-15, Q-MOV-04) move quantity from `pending` into a bucket in one guarded UPDATE, so pending can never go negative. The report then never derives history. |
| SA-MOV-03 | Columns map to fields: Memo = received; Return = returned; Sold = sold; Reserve = reserved; Outstanding = pending. Document rows sum their items. |
| SA-MOV-04 | Rows listed: `memo_receive.status = 'APPROVED'` with at least one item where `reserved > 0 OR pending > 0` (pcs or weight), Q-MOV-02. Filters: `q` (ILIKE doc no or vendor name snapshot, escaped, ≤ 100), `vendorIds` (≤ 50 uuids), `from/to` on doc date (≤ 366 days, Q-MOV-03). |
| SA-MOV-05 | `vendorList` uses **offset paging** (the design has a numbered pager): `page ≥ 1`, `pageSize ∈ {10, 25, 50}`, plus `total`. Sort whitelist: `docNo`, `dueDate` (default asc, then docNo), `vendorName`, `memoPcs`, `returnPcs`, `soldPcs`, `reservePcs`, `outstandingPcs`, `openValue`; `dir` asc or desc; tie-break id. One grouped SQL query (`GROUP BY memo_receive.id`) plus a count. Offset is acceptable at this data size (thousands of documents); measure it at 50k. |
| SA-MOV-06 | Open value per item = `line_amount × (reserved_basis + pending_basis) ÷ received_basis` (basis = weight for PER_CT, pcs for PER_PCS; a zero basis uses `net_unit_price × open qty`), 2 dp half-up, in the document currency. A document sums its items. Item price shown = `net_unit_price` + unit (Q-MR-13). |
| SA-MOV-07 | `vendorSummary` returns the counts and the grand total for the same filters. **documents** = rows listed. **overdue** = `due_date < today`. **dueIn7Days** = `today ≤ due_date ≤ today + 7`, with today in Asia/Bangkok. **grandTotal** = Σ open value × rate, where rate = `exchange_rate`, or 1 when the currency equals the company currency, and the result is in `companyCurrency` (Q-MOV-05). One aggregate query. |
| SA-MOV-08 | `vendorItems {memoReceiveIds ≤ 25}` returns the items of those documents only (approved, rows as in SA-MOV-04), ordered by doc then line position. Worst case is 25 × 200 = 5,000 rows, in one query. Each row carries `photoCount` only, no photo bytes. |
| SA-MOV-09 | `vendorOptions` lists the distinct vendors that have approved Memo Receive documents (id, code, name), ≤ 1,000, ordered by name. It is for the Vendor filter, so the page needs no `vendor:VIEW`. |
| SA-MOV-10 | Grants: every procedure needs `memo-outstanding-vendor:VIEW` (existing catalog leaf, all nine actions). `MasterMenu` gains `memo-outstanding-vendor`. PRINT and EXCEL are frontend-only, and Excel is unavailable (Q-MOV-08). Prices go to every VIEW holder (Q-MOV-07). |
| SA-MOV-11 | Not in this revision: writers for the Return, Sold and Reserve buckets, Excel export, the From Customer report, and a PRICE gate. |
