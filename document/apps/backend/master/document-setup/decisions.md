# SA decisions: document-setup revision 1

- Feature ID / SA revision / source UI revision: `document-setup` / 1 / UI rev 1 ([ui-spec](../../../frontend/document-setup/ui-spec.md))
- Status: **approved and implemented** — owner 2026-10-23: "frontend backend เริ่มทำ Document Setup เลย" (instruction to implement UI rev 1 with the proposed defaults Q-DS-01…10 and the API/permission proposal in [data-fetching.md](../../../frontend/document-setup/data-fetching.md)). The table design below is the backend detail of that approved proposal.
- Service: `backend-api-master` (owns PostgreSQL schema `partner`; master data). No new service, container, network, volume or package.

| ID | Decision |
|---|---|
| SA-DS-01 | Storage in schema `partner`: `document_setup` (PK `transaction_key` varchar(40); `name` varchar(120); `code` varchar(10) UPPERCASE, unique; `start_from` int 1–999,999,999; `declaration` varchar(2000) default ''; `version` int ≥ 1; `updated_by`; `updated_at`) and `document_numbering` (`id` uuid v7; `transaction_key` FK → `document_setup` ON DELETE CASCADE; `effective_date` date; `prefix` varchar(10) `^[A-Z0-9./-]{0,10}$`; `separator` varchar(3) `^[-/._]{0,3}$`; `start_no` int 1–999,999,999; unique (`transaction_key`, `effective_date`)). CHECK constraints in migration `20261023090000_document_setup` (expand-only). |
| SA-DS-02 | Fixed transaction list in code (`src/document-setup/document-setup.transactions.ts`): 15 keys = their permission menu keys, each with a label and default code (Q-DS-01). Unknown key → `DOCUMENT_SETUP_NOT_FOUND` (404) / tRPC input rejects it (400). |
| SA-DS-03 | tRPC `documentSetup.list` (VIEW) → `{items: {transactionKey, label, defaultCode, configured, code}[]}`; `documentSetup.get({transactionKey})` (VIEW) → `{setup: Setup \| null}`; `documentSetup.save(input)` (EDIT + CSRF) → `{setup}`. `Setup = {transactionKey, name, code, startFrom, declaration, version, updatedAt, rows: {id, effectiveDate "YYYY-MM-DD", prefix, separator, startNo, used}[]}` with rows sorted by date. |
| SA-DS-04 | Save is a whole replacement in one transaction: code clash with another transaction → `DOCUMENT_SETUP_CODE_TAKEN` (409, fieldErrors `code/duplicate`); `expectedVersion: null` creates (a parallel first save → `DOCUMENT_SETUP_CHANGED`), otherwise optimistic `version` match else `DOCUMENT_SETUP_CHANGED` (409); rows are replaced. (Replaces the `expectedUpdatedAt` idea in the UI draft; same behavior, matches Company Profile.) |
| SA-DS-05 | Permission: new auth catalog leaf `document-setup` under SETUP with actions VIEW and EDIT only (Q-DS-07). Catalog now 40 leaves / 349 applicable cells; existing grants unchanged. `MasterMenu` gains `document-setup`. |
| SA-DS-06 | Rules (owner text): a row applies from its date until the next row's date; document number = prefix + separator + running number, no padding (Q-DS-04/05); no automatic yearly reset (Q-DS-08). `used` is always false until transactions issue numbers; locking used rows (Q-DS-06) and issuing numbers belong to each transaction's future feature. "In use / Upcoming" is computed in the browser from today's date. |

Verification: master unit tests UT-DS-B01…B08 + router GP-MT-DS; migration applied in dev with no drift for these tables; live checks through nginx (list 15 items, get null, save, stale save → CHANGED, code clash → CODE_TAKEN; test row removed afterwards).
