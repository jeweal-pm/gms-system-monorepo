## Evidence and impact

- Affected files and line numbers:
  - `backend-api-inventory/src/app.ts` L113: `await c.req.formData()` parses (buffers) the entire multipart body, up to `PHOTO_BODY_MAX` (5 MiB + 64 KiB, L27/L81-82), before any concurrency bound.
  - `backend-api-inventory/src/modules/load-to-stock/photos.ts` L54, L65-66: the `Limiter(3)` for writes is entered only inside `upload()`, after the body is already buffered; inside it `file.arrayBuffer()` makes a second full copy.
  - `docker-compose.yml` backend-api-inventory: 256 MiB memory limit, `--max-old-space-size=160`; `docker/nginx/gms-dev.conf` inventory photo location has `client_max_body_size 6m` and no `limit_conn` / `limit_req`.
- Attacker prerequisites and reachable entry point: a signed-in, licensed user with `load-to-stock:ADD` or `EDIT` sending concurrent `POST /api/inventory/v1/load-to-stock/photos` requests through nginx (CSRF requires a trusted Origin, so this is the user's own client, not a cross-site attacker).
- Concrete trust boundary and source-to-sink trace: request body → `bodyLimit` (per-request cap only) → `requireSession` → handler `formData()` (≈ 5 MiB per request held in memory) → `photos.upload` limiter (3) → `arrayBuffer()` copy. N concurrent requests hold ≈ N × 5 MiB before the limiter refuses with 429.
- Observed impact: roughly 25-40 concurrent uploads approach the 256 MiB container limit, risking an OOM kill of the whole inventory service (all Load to Stock users, saga sweep). Not reproduced; static reasoning only.
- Missing validation fact / capability: actual Hono/undici multipart memory profile under concurrency and container RSS at the limit (no sandboxed load test run).
- Raw report/run links: none (focused review).

## Proposed work

- Allowed code scope and assigned implementation role: backend, `backend-api-inventory/src/app.ts` and `src/modules/load-to-stock/photos.ts` (+ their tests). Optional infra follow-up for an nginx `limit_conn` on the inventory photo location (parent-serialized shared file).
- Suggested remediation: acquire the write limiter (or a separate small upload-in-flight counter, e.g. ≤ 3) before `c.req.formData()` and refuse immediately with 429 `RATE_LIMITED` + `Retry-After` when full; avoid the second full copy where possible (reuse the parsed bytes). Optionally add a per-IP `limit_conn` for `/api/inventory/v1/load-to-stock/photos` in nginx.
- SA design / contract / flow / dependency change needed: no (429 `RATE_LIMITED` is already in the error catalogue).
- Acceptance criteria: with the limiter full, a further upload is refused with 429 before its body is parsed; a test proves at most the configured number of upload bodies are parsed concurrently; existing photo tests still pass.
- Safe verification plan and prerequisites: unit/integration test with a stubbed slow storage and concurrent uploads; optional bounded load test in a local container only.
