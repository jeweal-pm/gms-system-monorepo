แจ้งเตือนสถานะ
ให้ผู้ใช้อื่นเห็นแบบ Real Time

เอกสารนี้อธิบายแนวทางที่ทีมใช้คุยต่อได้: เมื่อรายการเปลี่ยนสถานะ เช่น Revise หรือ Reject ผู้ใช้ที่เกี่ยวข้องจะเห็นแจ้งเตือนเร็ว โดยระบบยังเก็บรายการไว้ให้เปิดดูย้อนหลังและตามทันหลังกลับมา online

หน้าเว็บ: TanStack Query + tRPC NestJS · @Sse + RxJS Hono · streamSSE (ทุก module ใน api-inventory) เก็บรายการ: PostgreSQL ไม่เพิ่ม client library สำหรับ EventSource

สถานะของแนวทางนี้

มีอยู่ในระบบ/สถาปัตยกรรมปัจจุบัน

Nginx route ตรงไปยัง domain API; api-master ใช้ NestJS และ domain tRPC สำหรับ master/เอกสารที่อยู่ใน service นี้. PostgreSQL เป็นฐานข้อมูลหลักของข้อมูลธุรกิจ.

เป้าหมายที่วางไว้

Hono · api-inventory ใช้ร่วมกันกับ Inventory, Sale, Account Outstanding และรายงานในภาพ; stream เดียวของ service นี้รองรับ notification จาก module เหล่านี้เมื่อเปิดใช้งาน. ตามทิศทางที่เลือก workspace/runtime ใช้ชื่อ backend-api-inventory; SA ต้องปรับชื่อ DNS/Compose ให้ตรงกับ API route api-inventory ก่อน implement.

ยังไม่ได้ติดตั้ง/ยังต้องออกแบบ

Notification feature, ตาราง/endpoint, SSE stream, วิธีรวม feed ข้าม service และการยืนยันตัวตนบน SSE ยังไม่มี contract หรือ implementation ที่อนุมัติ.

ใครเป็นเจ้าของ notification?

หลักที่เสนอ: service ที่เปลี่ยนสถานะของรายการเป็นผู้บันทึก notification และเป็นแหล่งข้อมูลจริงของ notification นั้น ไม่มี notification gateway/service กลางเพิ่มเข้ามาใน flow นี้

กลุ่มงานเจ้าของข้อมูลตามแนวทางปัจจุบันการแจ้งเตือนที่คาดว่าจะเป็นเจ้าของสถานะ
Master และเอกสารที่อยู่ใน api-master
เช่น Quotation, Purchase Order, Purchase ตาม ADR ที่เกี่ยวข้อง		NestJS · api-masterเหตุการณ์และ notification ของเอกสารเหล่านี้Service มี; notification ยังไม่มี contract
Inventory
Load to Stock, Merge/Split, Stock Transfer Location, Stock Adjustment, Barcode Printing		Hono · api-inventorymodule ภายใน service เดียวกัน บันทึก notification และส่ง SSE ผ่าน stream ของ api-inventoryเป้าหมาย; ยังไม่มี service ใน runtime
Sale, Account Outstanding และ Reports
Stock Movement, Closing Stock, Sale Report		Hono · api-inventorymodule ภายใน service เดียวกัน ใช้ notification storage/API และ SSE stream ของ api-inventory; สิทธิ์และข้อมูลยังแยกตาม moduleทิศทางที่กำหนดสำหรับเอกสารนี้; contract/schema ต้องออกแบบใน SA

Flow ตั้งแต่กดเปลี่ยนสถานะจนผู้รับเห็น

SSE เป็นช่องทางส่งสัญญาณทางเดียวจาก server มาที่ browser. การโหลดรายการและบันทึก read state ใช้ API ของเจ้าของ notification; protocol/route ที่แน่นอนต้องระบุใน SA contract.

SSE + API query

แต่ละ backend ใช้อะไรส่ง notification?

ใช้ SSE ซึ่งเป็น HTTP stream ทางเดียวจาก backend ไป browser. ไม่จำเป็นต้องเพิ่ม Socket.IO หรือ notification server แยกสำหรับ flow นี้.

ฝั่งระบบเครื่องมือ SSEแพ็กเกจ/สถานะในโปรเจกต์หน้าที่
NestJS · api-master@Sse() และ MessageEvent จาก @nestjs/common พร้อม Observable จาก rxjs@nestjs/common และ rxjs ติดตั้งอยู่แล้วใน api-masterเปิด endpoint SSE และปล่อย event จาก stream ของ NestJS
Hono · api-inventorystreamSSE() จาก hono/streamingเป็น helper ที่มากับแพ็กเกจ hono; ตัว Hono service ยังเป็นเป้าหมายและยังไม่ได้ติดตั้งใน workspaceเปิด SSE stream ให้ module Inventory, Sale, Account และ Reports ภายใน service เดียวกัน
Browser · frontendWeb API EventSourceมีใน browser; ไม่ต้องติดตั้ง client library เพิ่มสำหรับ SSEเชื่อมต่อและรับ event แล้ว refetch รายการจาก API
เครื่องมือเหล่านี้ทำหน้าที่ส่ง stream เท่านั้น
ยังต้องออกแบบที่เก็บ notification แบบถาวร, การผูก event กับ transaction, recipient rules และการกระจาย event เมื่อมีหลาย instance. RxJS stream หรือ Hono streamSSE() ไม่ใช่ message broker และไม่ทดแทน database/outbox.

แล้วหน้าบ้านต้องทำอะไรบ้าง?

โหลดเมื่อเข้าแอป

  • โหลด unread count และรายการล่าสุดของผู้ใช้ปัจจุบันจาก API เจ้าของ notification
  • เปิด EventSource แบบ same-origin ผ่าน Nginx ไปยัง api-master และ api-inventory; Hono stream ครอบคลุม module ทั้งสี่กลุ่มตามตารางด้านบน
  • ใช้ credential ที่ผ่านการอนุมัติใน auth contract; server ระบุตัวผู้ใช้จาก credential และไม่รับ user ID ที่ client เลือกเอง

รับเมื่อมี event

  • รับ event เช่น notification.created
  • ใช้ ID เป็นสัญญาณ แล้ว refetch จาก API; ไม่ใช้รายละเอียดจาก push เป็นแหล่งข้อมูลจริง
  • อัปเดต unread badge / toast / notification list ตามหน้าที่เปิดอยู่

เปิดเมื่อกดแจ้งเตือน

  • นำทางไปยังหน้ารายการที่เกี่ยวข้อง
  • โหลดรายละเอียดจาก API เจ้าของรายการ ซึ่งตรวจสิทธิ์ซ้ำทุกครั้ง
  • เมื่อทำเครื่องหมายอ่าน ให้บันทึก read state ของผู้ใช้นั้นผ่าน API เจ้าของ notification

หลุดเมื่อ offline / reconnect

  • ถ้าหลุด SSE, browser พยายามเชื่อมต่อใหม่ตามกลไก EventSource
  • เมื่อกลับมา online ให้โหลด unread/list ล่าสุดจาก API เพื่อเก็บ event ที่พลาด
  • ใช้ notification ID ป้องกันแสดงรายการซ้ำ

ถ้าหน้ากระดิ่งต้องรวมหลาย service

  1. การเชื่อมต่อ: browser เปิด stream แยกสอง API ผ่าน same-origin Nginx: NestJS api-master สำหรับเอกสารฝั่ง master และ Hono api-inventory สำหรับ Inventory, Sale, Account Outstanding และรายงาน.
  2. ข้อมูลในกล่อง: แต่ละ API คืนรายการและ unread count ของตัวเอง; frontend รวมเพื่อแสดงผลชั่วคราวได้ แต่ต้องกำหนดการเรียงเวลา, pagination และ read state แยกเจ้าของ.
  3. เมื่อกดรายการ: ใช้ deep link ไปหน้ารายการ แล้วโหลดข้อมูลจาก API เจ้าของรายการพร้อมตรวจสิทธิ์ใหม่.
  4. ข้อจำกัด: cursor/pagination แบบรวมข้าม service และ unread total เดียวที่แม่นยำต้องมี contract เพิ่ม; อย่าให้ frontend เขียนฐานข้อมูลหรือส่งคำสั่งข้าม service โดยตรง.

ข้อมูลอะไรวิ่งทางไหน?

DBข้อมูลถาวรในฐานข้อมูล

รายการแจ้งเตือน, ผู้รับ, เวลา, read state และ reference ไปยังรายการงาน เก็บในขอบเขตข้อมูลของ API เจ้าของ notification ตาม contract ที่ออกแบบ

เป็นแหล่งข้อมูลจริง

SSEข้อมูล push แบบ real time

ส่งสัญญาณขนาดเล็ก เช่น type และ notificationId ให้ browser รู้ว่าควรโหลดข้อมูลใหม่

ส่งเร็ว ไม่ใช้แทน database

จุดความปลอดภัยที่ต้องมี

ตรวจสิทธิ์ตอนเชื่อมต่อกำหนด credential/cookie, origin, หมดอายุ และ logout behavior สำหรับ SSE; รายละเอียดนี้ยังต้องอยู่ใน contract
ส่งเฉพาะผู้รับที่ถูกต้องbackend คำนวณกลุ่มผู้รับจากกติกางาน ไม่รับ recipient list ที่ client กำหนดเอง
ไม่ส่งข้อมูลลับผ่าน eventpush ID/ชนิดเหตุการณ์ แล้วให้ API เจ้าของข้อมูลโหลดรายละเอียดพร้อมตรวจสิทธิ์
ป้องกันการเชื่อมต่อเกินขอบเขตจำกัด origin, จำนวน connection และข้อมูลค้าง พร้อม log โดยไม่บันทึก session token

สิ่งที่ทีมต้องตัดสินใจใน SA contract

เอกสารนี้เป็น team brief สำหรับแนวทาง ยังไม่ใช่ข้อกำหนดที่อนุมัติให้ implement
การเลือก SSE และรูปแบบ notification store, endpoints, event names, recipient rules, retention และ feed ข้าม service ยังต้องออกแบบ/อนุมัติ. แนวทางนี้เพิ่ม notification ใน domain API เจ้าของงาน และไม่เพิ่ม gateway หรือ notification service แยกในตอนเริ่มต้น.
  • กติกาผู้รับ: ใครควรเห็น revise/reject/status change ในแต่ละชนิดเอกสาร และการเปลี่ยนสถานะแบบใดควรส่ง notification
  • ความทนทาน: สถานะธุรกิจและ notification ต้อง commit อย่างสอดคล้องกัน; ถ้าแยก transaction/storage ต้องออกแบบ outbox หรือกลไกเทียบเท่า
  • การ scale: หลาย API instance ต้องกระจาย event ได้ครบ; ยังไม่ควรเพิ่ม Redis/broker จนมีเหตุผลและ capacity design ที่อนุมัติ
  • พฤติกรรม reconnect, heartbeat, retry, retention, การลบ/ซ่อน และ pagination ต้องกำหนดให้ชัด
  • ทำชื่อ service ให้ตรงกันใน ADR/spec/Nginx/Compose: API route api-inventory; workspace/runtime target backend-api-inventory
  • ยืนยันต้นทุน connection/DB pool และ resource limits บน host 4 GB / 2 vCPU ก่อนเปิดใช้จริง
