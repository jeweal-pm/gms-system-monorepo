## Context

Load to Stock takes the lines of approved Purchases that have no Stock ID (MANUAL / PURCHASE_ORDER, ADR-0051) into the company's own stock, fully or partly, in one of three modes per document (None / Split / Merge). With approval ON the PU is deducted and stock created at Approve; with approval OFF at Save, and the document stays editable/deletable until its stock is used (ADR-0050).

Facts from the checkout (2026-11-16, branch `feat/16-11-26-load-ui` at `2e87a5b`):

- No inventory service, schema or own-stock table exists. ADR-0027 approved an inventory boundary (`/api/inventory/v1`, schema `inventory`, Hono proposed) but no slice.
- Purchase, its lines (`partner.purchase_line`, no "loaded" bucket), Document Setup (`load-to-stock`, code `LS`, already seeded), the Approval Setting row `load-to-stock` (inactive), the Stock ID counter `partner.memo_stock_id_counter` and `issueStockIds` all live in `backend-api-master` (`api-master`), schema `partner`.
- The auth catalog already has leaves `load-to-stock` (all nine actions) and `location-master` (no API).
- Compose today: postgres 0.60 / 1024 MiB, auth 0.30 / 512, api-master 0.25 / 384, frontend 0.30 / 640, nginx (GMS overlay) 0.10 / 64 = **1.55 vCPU / 2624 MiB** on a 2 vCPU / 4096 MiB host.
- INV-20261113-001 Part B (Stock ID duplicate across tables at the Bangkok New Year boundary) was closed only because Purchase stopped issuing. A second issuer re-opens it unless issuing is serialized.

The owner-selected boundary (SA skill, 2026-11-16) puts Inventory (Load to Stock, Merge/Split, Stock Transfer Location, Stock Adjustment, Barcode Printing), Sale, Account Outstanding and the Stock Movement / Closing Stock / Sale reports in **one** Hono service `backend-api-inventory`, with internal module boundaries; grouping does not permit cross-schema writes, direct reads of another service's tables or a shared transaction across owners.

## Decision

**D1 — Service identity and scope.** New workspace `backend-api-inventory` (package `@gem-crm/backend-api-inventory`), Hono on Node 24 via `@hono/node-server`, Compose service and DNS name **`backend-api-inventory`**, port **3301**, internal only. Nginx routes `/api/inventory/` to it (same origin, no gateway). It owns PostgreSQL schema **`inventory`** with its own login role. Module folders: `src/modules/load-to-stock/` now; `merge-split`, `stock-transfer`, `stock-adjustment`, `barcode`, `sale`, `account-outstanding`, `reports` later in the same process, each owning its own tables inside schema `inventory` and calling each other only through module service interfaces (no module writes another module's tables). This replaces ADR-0027's working name `api-inventory`.

**D2 — Public API.** Typed REST JSON under `/api/inventory/v1` (ADR-0025 D1: inventory uses REST; no tRPC), Zod 4 validation, the GMS error envelope `{error:{code,message,requestId,details?}}`, cookie access JWT verified locally (jose, auth JWKS), live authorization from the auth-owned view through a dedicated read-only role, license through auth with an inventory-specific service token, Origin/Fetch-Metadata CSRF on every mutation (as ADR-0031 master). Contract: [api-contract](../apps/backend/inventory/load-to-stock/api-contract.md).

**D3 — Ownership of Purchase remaining (amends nothing in Purchase semantics).** Master stays the only writer of Purchase data. It gains `purchase_line.loaded_pcs` / `loaded_weight_ct` (CHECK 0 ≤ loaded ≤ line qty; STOCK lines always 0) and a per-load allocation ledger (`partner.load_allocation`, `partner.load_allocation_line`). Remaining = line qty − loaded. Drafts and pending loads hold nothing (Q-LS-06).

**D4 — Cross-service consistency: idempotent "set allocation" + local saga.** Inventory never writes `partner`. To apply a load (Save with approval OFF, Approve with ON, Edit/Delete/Restore of an applied load) inventory:

1. in its own transaction, marks the load `sync_state = SYNCING` (guarded by `version`) and stores a `master_sync_op` row (`load_id`, next `revision`, the full desired allocation, request hash);
2. calls master `PUT /internal/v1/inventory/load-allocations/{loadId}` with `{revision, vendorId, lines[{purchaseLineId,pcs,weightCt}], newStockIdCount}`. In **one master transaction** master locks the allocation header, then the Purchase headers `FOR SHARE` and the lines `FOR UPDATE` in id order, checks each PU is APPROVED, not deleted, same vendor, MANUAL/PO, and the delta against remaining, sets `loaded_*`, replaces the allocation lines, issues `newStockIdCount` Stock IDs (D5) and stores the result. Same revision + same hash replays the stored result; a lower revision or a changed hash is refused. An empty `lines` releases everything;
3. in a second local transaction, creates/updates/reverses the stock rows with the returned Stock IDs, appends movements, sets the final status and `sync_state = IDLE`.

A business refusal in step 2 (e.g. not enough remaining) rolls the load back to its previous state and returns the row error. A timeout/5xx leaves the op `PREPARED`; it is re-driven with the same revision and payload (safe because step 2 is idempotent) on the next access to that load, at service start, and by a bounded in-process sweep (every 60 s, ≤ 20 ops, no queue, no Redis). While `SYNCING`, the load and its stock are locked for every other change (`LOAD_TO_STOCK_BUSY`). No HTTP call is made while a database transaction is open.

**D5 — Stock ID (amends ADR-0051 §6).** The Stock ID is issued **when the stock is created** — at Save with approval OFF, at Approve with ON — one per load row (Split: one per child; Merge: one), by master inside the D4 allocation transaction from the existing `memo_stock_id_counter` (same `YY####` format, e.g. `260123`). Rows kept by an edit keep their ID; removed rows retire theirs; IDs are never reused (also after delete/restore). Master records every Load-issued ID in `partner.load_stock_id` (PK `stock_id`) for idempotent replay and audit. To keep Memo Receive and Load to Stock from duplicating an ID across tables at the New Year boundary (INV-20261113-001 Part B), `issueStockIds` is changed for **both** callers to take one fixed transaction advisory lock first and compute the year from the clock **after** the lock. Before the ID exists the UI shows "Auto".

**D6 — Own stock model (refines ADR-0027 D2 for gemstones).** Inventory stores one row per Stock ID in `inventory.stock` (location, parcel, stone attributes, pcs, weight, on-hand pcs/weight, price unit, company-currency cost unit price and amount, stock price, sale price, vendor snapshot, `first_used_at`), its photos in `inventory.stock_photo`, and an append-only `inventory.stock_movement` ledger (`LOAD_IN`, `LOAD_ADJUST`, `LOAD_REVERSAL`; later modules add their kinds). The generic item/SKU/unit/lot/balance model of ADR-0027 is not built: a gemstone lot is identified by its Stock ID, and a separate balance table would duplicate `stock.on_hand_*`. Locations come from master's Location Master (ADR-0053) and are stored as a name snapshot (D11).

**D7 — Document, modes and cost.**

- One mode per document (`NONE` / `SPLIT` / `MERGE`, Q-LS-07): stored on the header; changing it needs an empty Load table.
- Tables: header `load_to_stock`, picked PU lines `load_to_stock_source`, load rows `load_to_stock_row`, and the many-to-many `load_to_stock_row_source` (Split: one source → many rows; Merge: many sources → one row; None: one → one).
- Merge (Q-LS-08): ≥ 2 sources, price units may be mixed, full remaining quantity of every source, pcs/weight locked; the row's details and initial photos come from the source with the highest company-currency amount per piece; the merged row's price unit is PER_CT unless every source is PER_PCS.
- Cost (Q-LS-03/12): kept in the **company profile currency** (owner Q-LS-23), snapshot on the header as `currency_code`. Per source: unit cost (company currency) = PU line net unit price (after the line discount) × the PU's exchange rate to the company currency (1 when the PU is in that currency); amount = loaded weight (PER_CT) or loaded pcs (PER_PCS) × unit cost, 2 dp half-up. A row's cost = Σ of its sources. PU header discount, tax, charges and labor are not allocated (Q-LS-24).
- Stock Price and Sale Price are required, start empty, ≥ 0, per the row's price unit, in the company currency (Q-LS-13, Q-LS-23).
- When a PU line's remaining pcs reaches 0 the line closes and is no longer shown; weight left over is written off on that line (Q-LS-21). A line is loadable only while remaining pcs > 0, so a PU line with pcs 0 is never offered. A load row has pcs ≥ 1; its weight may be 0 only when its source line's weight is 0 (owner Q-LS-26).
- Later picks in a document use the document's mode: in the mode dialog the other modes are disabled with "This document is in {mode} mode"; in a Merge document the newly picked lines join the single merged row, which is recomputed (still ≥ 2 sources).

**D8 — Approval setting ownership (amends ADR-0050 D1, recommended default of Q-LS-25).** The switches of inventory types (`load-to-stock`, `merge-split`, `stock-transfer-location`) move to `inventory.approval_setting`, because ADR-0050 D5 requires the setting to be read `FOR SHARE` inside the same transaction as the document Save and the turn-OFF guard to count waiting documents under the setting lock. Master deletes its three inactive rows and narrows its CHECK; the Approval Setup page reads/writes those three through inventory (same shape), and `useApprovalSetting("load-to-stock")` reads inventory. The status model of ADR-0050 D2 (Draft → Send to approve → Pending (locked) → Approve / Revise once / Reject) and D6 Daybook apply unchanged.

**D9 — Edit-until-used (amends ADR-0050 D4).**

| Type | Used when |
|---|---|
| Purchase (replaces the "not built" row) | any of its lines has `loaded_pcs > 0` or `loaded_weight_ct > 0` (an applied Load to Stock). Drafts / pending loads do not make it used. Master's Purchase edit/delete then returns `PURCHASE_IN_USE`. |
| Load to Stock (new row) | any stock it created currently has quantity outside on-hand (`on_hand_pcs <> pcs OR on_hand_weight_ct <> weight_ct`): reserved or memo-out by a master document (D15), consumed by Merge/Split, Transfer, Adjustment, or sold. Drafts/pending documents and Quotation (copy only) never make it used. Releasing the hold makes it editable again (current-state rule, like Memo Receive). Until D15 phase 2 and the other inventory modules exist, an auto-approved load is always editable. Refused with `LOAD_TO_STOCK_IN_USE`. `first_used_at` is kept as an audit timestamp only. |

Edit of an auto-approved load re-applies through D4 (one allocation call with the new set); Delete releases everything and soft-deletes (ADR-0045 columns) the document and reverses its stock. **No Restore** (owner Q-LS-33): a deleted Load to Stock stays deleted and visible read-only in the Deleted filter; this amends the ADR-0045 item 8 convention for this document type.

**D10 — Numbering.** Document Setup stays in master. Inventory calls `POST /internal/v1/inventory/document-numbering/resolve` (`transactionKey: "load-to-stock"`, `docDate`, `markUsed`) to get the numbering row in effect; with `markUsed: true` master sets `document_numbering.external_used_at` so the row becomes locked like a row used by a master document. Inventory computes the running number (`max(running_no) + 1` per numbering row, under a transaction advisory lock) in its own table, as the master engine does. The number is assigned at the first Save (Draft or applied).

**D11 — Locations (aligned with [ADR-0053](0053-location-master.md), Accepted).** Location is a required select that **starts empty** (owner Q-LS-28), even though the PU line now carries a location name chosen from the same master: the PU location is shown read-only in the Item table (IT-3) and the user picks the load row's location. Location Master is owned by `backend-api-master` (`partner.location`: id, name ≤ 40 unique ignoring case, active; router `locationMaster`). Following ADR-0053 D2, inventory keeps the location **name as text**, not an id: (1) options come through inventory `GET /load-to-stock/options`, which reads master's internal `GET /internal/v1/inventory/reference` returning `locations: string[]` (active names, ≤ 500, the same list as master's `options.locations`); (2) at Save inventory checks every row's name and every `stoneCodeId` in **one** call `POST /internal/v1/inventory/master-data/resolve {stoneCodeIds, locationNames}`: a name matches an active location **case-insensitively** and master returns its own spelling, which inventory stores; on update a row may keep the name it already has even if that location was later renamed or deactivated (ADR-0053 D3); anything else → `LOCATION_INACTIVE`; (3) `load_to_stock_row.location` and `stock.location` are `varchar(40)` name snapshots, no id or foreign key; renaming or deactivating a location never changes saved loads or stock. Inventory has no location table and no location write endpoint.

**D12 — Approve Center and notifications.** Inventory serves `GET /approval/summary` and `GET /approval/pending` for its types with the master shapes, and the approve/revise/reject mutations per document. The frontend merges master and inventory summaries. Inventory owns its notification feed (`inventory.notification_event` / `notification_recipient`, same contract as ADR-0049, written in the status-change transaction) and its own SSE stream `GET /api/inventory/v1/notifications/stream` (Hono `streamSSE`), ids only; the bell shows two feeds and adds the unread counts (ADR-0049 D10; path now under `/v1`). Recipients come from the auth view `auth.permission_holders` (granted read-only to the inventory reader role). No central notification service or broker.

**D13 — Photos.** Load rows and stocks have ≤ 5 photos (ADR-0048 rules: JPEG/PNG ≤ 5 MB, signature check). Uploads go through `@gms/storage` (local fs driver) under `files/load-to-stock/` in inventory's own storage root; metadata in `inventory.stored_file`. PU line photos are copied once per master file (`POST …/photos/from-purchase-line`, streamed from a master internal endpoint, deduplicated by `origin_file_id`). User-uploaded bytes and their metadata are kept permanently; removing a photo in the UI only unlinks it (ADR-0030). S3 is not implemented (proposed profile only).

**D15 — Own stock in every "From Stock" picker (owner Q-LS-30, phased).** The owner confirmed (and ADR-0038 already said) that From Stock lists Memo Stock **and** our own stock.

- *Which pickers:* customer-side From Stock — Quotation (copy only, nothing held, ADR-0038), Reserve (hold), Memo Out (moves out to the customer; Memo Out Return brings it back) and later Sale (inventory). Purchase `STOCK` rows and Memo Return stay Memo-Stock-only: they settle or return goods still owned by the vendor, while own stock is already bought (Q-LS-35).
- *Ownership:* inventory stays the only writer of own stock. `inventory.stock` gets buckets `reserved_pcs/_weight_ct`, `memo_out_pcs/_weight_ct`, `sold_pcs/_weight_ct`, `consumed_pcs/_weight_ct` with CHECK `pcs = on_hand + reserved + memo_out + sold + consumed` (same for weight) and all ≥ 0. Holds per document live in `inventory.stock_hold` (document type, document id, line id, stock, kind, pcs, weight) with `stock_movement` rows.
- *Master → inventory API (new direction):* `PUT /internal/v1/master/stock-holds/{documentType}/{documentId}` with set semantics, `revision` and request hash (mirror of D4); `GET` of the same for recovery; `POST /internal/v1/master/stock/batch` (≤ 200 ids, availability) for Save validation. Master runs the mirror saga (`partner.inventory_sync_op`, `sync_state` on its document headers, 60 s bounded sweep) at Approve / auto-approved Save / edit / delete of Reserve, Memo Out and Memo Out Return. Credential `MASTER_INVENTORY_SERVICE_TOKEN` (separate from the inventory → master token). Master lines gain source `OWN_STOCK` with `stock_uuid` and the Stock ID snapshot.
- *Picker read:* the browser reads own stock directly from inventory `GET /api/inventory/v1/stock/available` (keyset ≤ 50, VIEW on any of quotation / reserve / memo-out / load-to-stock), shown as a second section/tab next to Memo Stock; no merged cross-service cursor.
- *Phases:* **Phase 1 = this revision** — the stock buckets, CHECK, `stock_hold` table and the current-state "used" rule ship with Load to Stock, so no stock migration is needed later; nothing consumes own stock yet. **Phase 2a** — Quotation shows own stock (read-only, no hold; low risk). **Phase 2b** — Reserve, Memo Out, Memo Out Return hold/move own stock through the API above (needs the master saga). **Phase 3** — Sale in inventory consumes own stock locally and Memo Stock through a master API. Each phase needs its own UI revision (picker design) and SA revision; Load to Stock is not blocked by them because nothing can be picked before stock is loaded.
- *From Stock with two stocks — user-visible behaviour and limits (phases 2a/2b):*
  - The picker shows **two sections (tabs) — "Our stock" and "Memo Stock"** — with the same columns, one shared search box and the same date/location filters. Each section has its own server-side keyset paging (50, "Load more") and its own count; sort is the section's fixed order (Stock ID desc for own stock, as today for Memo Stock). There is **no merged list**: a merged sort/cursor across two services would need both services queried per page and an unstable combined cursor, for little benefit. Ticks can be made in both sections and are added together; the line source (`OWN_STOCK` / `STOCK`) is kept per line.
  - **Inventory down:** the Memo Stock section and documents with only Memo Stock lines work normally. The "Our stock" section shows "Our stock is unavailable — Retry". Save/Approve of a document that has own-stock lines is refused with `INVENTORY_UNAVAILABLE` (503, "Our stock can't be checked right now; try again"), with nothing changed; an unknown outcome after the hold call follows the saga (`SYNC_PENDING`, re-drive).
  - **Concurrent holds of the same own stock:** inventory locks the stock rows `FOR UPDATE` in id order inside the hold transaction; the first document wins, the second gets `STOCK_HOLD_EXCEEDS_AVAILABLE` → master returns its usual short error for that row ("Row n: only x pcs left"), exactly like two documents taking the same Memo Stock today. Drafts hold nothing; availability is re-checked at the hold.
- *Boundary warning:* with D15 most consumers of own stock are master documents, and Sale (inventory) will consume master's Memo Stock. Every stock-moving document on either side then needs a cross-service saga. The new-service boundary still works but costs a saga per stock-moving document type (Q-LS-36: owner chose to keep this boundary).

**D14 — Capacity.** `backend-api-inventory` limits: **0.20 vCPU, 256 MiB, Node heap `--max-old-space-size=160`, pids 128**, Prisma pool **max 5** (connect timeout 2 s) plus authz reader pool **max 1**. New Compose total **1.75 vCPU / 2880 MiB**, headroom ≈ 0.25 vCPU / 1216 MiB. Bounds: lists/pickers ≤ 50 per page, ≤ 200 load rows and ≤ 200 sources per document, ≤ 3 concurrent photo transfers, ≤ 200 SSE streams, master internal calls 5 s timeout with ≤ 4 sockets, sweep ≤ 20 ops/min. No Redis, worker or replica. D15 phase 2 adds no container: master gets an outbound client (≤ 4 sockets, 5 s), a 60 s sweep and one HTTP call per approve/save of a Reserve / Memo Out / Memo Out Return that has own-stock lines; inventory gets the inbound internal route; DB pools unchanged.

## Alternatives

| Alternative | Why not chosen |
|---|---|
| Load to Stock as a module in `backend-api-master` (one transaction, no saga) | Simplest and atomic, but contradicts the owner direction "สร้าง service ใหม่เลยไม่รวมกับ master" and the selected inventory boundary. |
| Inventory writes `partner.purchase_line` / the counter with a granted DB role, or calls a master-owned `SECURITY DEFINER` function inside its own transaction | Atomic, but it is a cross-schema write / shared transaction across owners, which the boundary rule forbids. Kept as an owner option (Q-LS-31) because it removes the saga. |
| Inventory keeps its own "loaded" ledger and master reads it | Two writers of one business fact; master's Purchase edit/delete would need a synchronous call to inventory under its locks. |
| Outbox + Redis/worker for the master call | Adds containers to a 4 GB host; the call is short and idempotent, so an in-process bounded re-drive is enough. |
| Keep the inventory approval rows in master and call inventory for the turn-OFF count | Leaves a race between a toggle and an inventory Save that ADR-0050 D5 explicitly closes with a shared lock (Q-LS-25 alternative). |
| A separate Stock ID counter in inventory | Two counters with the same format would collide; master's counter already guarantees one sequence. |
| tRPC in Hono (`@trpc/server` fetch adapter) | ADR-0025 fixed REST for inventory; tRPC would need a later approved contract. |

## Consequences and capacity

- **Master (backend-api-master) changes, additive:** migration adding `purchase_line.loaded_pcs/loaded_weight_ct` + CHECKs + a partial "loadable" index, `load_allocation`, `load_allocation_line`, `load_stock_id`, `document_numbering.external_used_at`; deletion of the three inventory rows of `approval_setting` with a narrower CHECK; `issueStockIds` serialization; an internal router `/internal/v1/inventory/*` behind a **new** service token; Purchase edit/delete guard `PURCHASE_IN_USE`; Document Setup "used" includes `external_used_at`.
- **Auth changes:** a reader role for inventory on `auth.current_authorization` and `auth.permission_holders`, and acceptance of an inventory service token on the license endpoint.
- **New:** container, image, schema, DB roles, nginx locations (`/api/inventory/`, its photo upload and SSE stream), secrets, storage path, CI build target. Infra and devops requirements: [handoff](../coordination/handoffs/load-to-stock-infra-devops.md).
- **Frontend:** a REST client for `/api/inventory/v1`, Approval Setup and Approve Center merge inventory types, the bell merges two feeds.
- **Rollback:** disable the nginx route and stop the container; master columns stay (defaults 0) and Purchase behaves as today. Applied loads cannot be undone by schema rollback: release them through the API (Delete) first, which returns PU remaining. The deleted approval rows are re-inserted by the down script.
- **Risk:** the saga adds states (`SYNCING`) and recovery code; it is covered by idempotency tests, kill-between-steps tests and the concurrent-approve test ([testing](../apps/backend/inventory/load-to-stock/testing.md)).
- **Capacity:** see D14; production measurement of the new image (idle and under a 200-row apply) is required before claiming fit.

- Status: **Accepted** (2026-11-18; owner 2026-11-18 "อนุมัติ UI rev phase 2 + SA rev 2" (Q-LS-P2-01…07 take the recorded answers/defaults; Q-LS-P2-02 Lot; Q-LS-P2-05 as explained in chat)). Phase-1 decisions above stay Accepted and implemented.

- Bundle: [decisions SA rev 2](../apps/backend/inventory/load-to-stock/decisions.md#sa-revision-2--phase-2a--2b-proposed), [api-contract](../apps/backend/inventory/load-to-stock/api-contract.md#phase-2-sa-revision-2-proposed), [sequence-diagram](../apps/backend/inventory/load-to-stock/sequence-diagram.md#phase-2-sa-revision-2-proposed), [database-diagram](../apps/backend/inventory/load-to-stock/database-diagram.md#c-phase-2-sa-revision-2-proposed), [error-handling](../apps/backend/inventory/load-to-stock/error-handling.md#phase-2-sa-revision-2-proposed), [testing](../apps/backend/inventory/load-to-stock/testing.md#phase-2-verification-plan-sa-revision-2-proposed); TODO BE-LS-P2-* in [task/todo/load-to-stock.md](../task/todo/load-to-stock.md); infra/devops delta in [load-to-stock-infra-devops](../coordination/handoffs/load-to-stock-infra-devops.md#phase-2b-delta-sa-revision-2-proposed).

**D16 — One From Stock list, merged by master (replaces D15 "Picker read" and "two sections").** The customer-side pickers (Quotation, Reserve, Memo Out) call a new master tRPC query `fromStock.list` (VIEW on any of quotation / reserve / memo-out); `memoStock.list` stays unchanged for Memo Return and the Purchase pickers (Q-LS-35).

- *Order and cursor:* both stocks are sorted by the existing Memo Stock key **(ref doc date DESC, Stock ID DESC)**; the ref date is the Memo Receive date for Memo Stock and the Load to Stock doc date for our stock. Stock IDs come from one counter (D5) and are unique across `partner.memo_stock` and `inventory.stock`, so this key is a **total order over both stocks**. The existing opaque cursor `base64url(date|stockId)` is therefore reused unchanged: each side applies `(date, stock_id) < cursor`. No composite or per-side cursor is needed, and paging is stable.
- *Per page:* master runs, in parallel, (a) its Memo Stock query `LIMIT limit+1` and (b) one call `POST /internal/v1/master/stock/available` to inventory with the same filters, the cursor key and `limit+1` (one indexed query on a new partial index). It merges the two sorted lists (≤ 102 rows), returns the first `limit`, and sets `nextCursor` to the key of the last returned row when either side still has rows. The cost is 2 queries + 1 HTTP call per page, whatever the row count (no N+1). There is no count.
- *Filters:* `q` (Stock ID, lot, stone, cer no, ref doc no), `from`/`to` (ref date), optional `location` (`Memo` → Memo Stock only, inventory not called; another name → our stock only, Memo Stock not queried). No vendor or currency (customer pickers list every vendor, as SA-MO-15).
- *Row shape:* the Memo Stock item plus `source: "MEMO_STOCK" | "OWN_STOCK"`; our stock rows have `location` = the stock's location name, `ref.type = "LOAD"` (already reserved in `StockSourceRef`), `load {id, docNo, docDate}`, `lot` (the stock's lot, shown as the Lot badge like Memo Stock; owner Q-LS-P2-02, D23), available = on-hand, and **no price** (price fields null, as ui-spec Q-LS-P2-03: the line's Sale Price starts empty and required). Cost is never sent to the picker.
- *Inventory down / slow (2 s read timeout):* the page returns Memo Stock rows only with `ownStock: "UNAVAILABLE"`. The UI shows "Our stock is unavailable — Retry" above the list, and Retry restarts from page 1. Memo Stock picking keeps working.
- *Why master merges, not the browser (decides ui-spec SA-LS-P2-01/02 and its Q-LS-P2-01 "merged in the browser").* The owner wants one list. Master already serves this picker and needs an inventory client for 2b anyway. A merge in the browser would need:
  - a second public route (`GET /api/inventory/v1/stock/available`) with its own permission check;
  - two cursors, plus the "show only up to the oldest reached key" bookkeeping;
  - partial-page logic in the client for each source.

  The server merge needs none of these. The cursor stays the single existing one, and the client keeps one `useInfiniteQuery`. A merge in inventory would make inventory read master's Memo Stock, which is the same cross-service read in the other direction. The order Q-LS-P2-01 asked for (ref doc date DESC, Stock ID DESC) is kept. Affected FE items:
  - FE-LS-P2-01 calls `fromStock.list` (master tRPC), with no inventory client.
  - FE-LS-P2-02 (browser merge) is **dropped**.
  - FE-LS-P2-03 reads `ownStock: "UNAVAILABLE"` for the notice. "You can't view our stock" goes away, because master authorizes the user. "Memo Stock is unavailable" is the whole query's error state.
  - FE-LS-P2-04 sends `ownStockId` (not `stockUuid`).

**D17 — Phase 2a: Quotation copies our stock (no hold).** `quotation_line` gets `own_stock_id` (inventory `stock.id`, no foreign key across services) and `source 'OWN_STOCK'`. Before its save transaction, master reads `POST /internal/v1/master/stock/batch` (≤ 200 ids) and copies the Stock ID, stone code and attributes, lot, location, cer and price unit, with the available quantity as the snapshot (`stock_pending_*`). It checks pcs/weight ≤ available. A line is **kept** without the call, using its stored snapshot, when the same stock is already on the stored quotation and its quantity is not raised, as the Memo Stock `kept` rule does. So a quotation with unchanged own-stock lines still saves while inventory is down. Otherwise the save gets `503 INVENTORY_UNAVAILABLE` and nothing is saved. A quotation never holds stock and never makes a load "used".

**D18 — Phase 2b: holds in inventory.** Inventory remains the only writer of our stock. Hold kinds per document type:

| Document | Kind | Bucket move per +q (reverse per −q) |
|---|---|---|
| Reserve | `RESERVED` | on-hand → reserved |
| Memo Out | `MEMO_OUT` | on-hand → memo_out |
| Memo Out Return | `MEMO_OUT_RETURN` | memo_out → on-hand |

Holds are stored per **(document type, document id, stock)** (`stock_hold`, re-keyed from `line_id`, which phase 1 never wrote), so line ids that change on edit do not matter. A `stock_hold_document` row per document keeps the applied revision, the request hash and the result. `PUT /internal/v1/master/stock-holds/{documentType}/{documentId}` sets the whole set in one inventory transaction:

1. Lock the document row.
2. Run the revision checks. A higher revision applies; the same revision with the same hash replays the stored result; anything else gets `409 STOCK_HOLD_STALE`. Gaps are allowed.
3. Lock the stocks `FOR UPDATE` in id order, joined to their load's `sync_state`.
4. Refuse any stock whose load is `SYNCING` (`409 STOCK_HOLD_BUSY`, SA-LS-18).
5. Check each per-stock delta. An increase of RESERVED or MEMO_OUT needs ACTIVE stock with on-hand ≥ q (`STOCK_HOLD_EXCEEDS_AVAILABLE` or `STOCK_HOLD_UNAVAILABLE`). A decrease of MEMO_OUT needs memo_out ≥ q, and a decrease of MEMO_OUT_RETURN needs on-hand ≥ q; otherwise `STOCK_HOLD_IN_USE`. An increase of MEMO_OUT_RETURN needs memo_out ≥ q (`STOCK_HOLD_EXCEEDS_MEMO_OUT`, a drift guard, because master checks outstanding first).
6. Move the buckets with one set-based UPDATE (the phase-1 CHECK keeps `pcs = Σ buckets`), replace the hold rows, and append movements (`HOLD_RESERVE`, `RELEASE_RESERVE`, `MEMO_OUT`, `MEMO_OUT_REVERSAL`, `MEMO_OUT_RETURN`, `MEMO_OUT_RETURN_REVERSAL`; the deltas are on-hand changes and cost delta is 0).

The transaction uses ≤ 8 statements for ≤ 200 stocks. **Load "used" (D9) is unchanged and now live:** any hold makes on-hand ≠ pcs, so the load becomes read-only (`LOAD_TO_STOCK_IN_USE`, details add `holders`), and releasing every hold makes it editable again.

**D19 — Phase 2b: master saga "acquire → local → release" (mirror of D4, master → inventory).** Reserve, Memo Out and Memo Out Return headers get `sync_state` (`IDLE`/`SYNCING`) and `hold_revision`. A new `partner.inventory_sync_op` holds one active op per document. For each operation that changes the document's applied hold set (approval OFF: create / edit / delete / restore; approval ON: Approve), master computes H_old (applied set) and H_new and splits the per-stock delta:

- **acquire** = changes that need free quantity in inventory and can be refused: RESERVED/MEMO_OUT up, MEMO_OUT_RETURN down;
- **release** = changes that cannot be refused by construction: RESERVED/MEMO_OUT down (this document's own holds; returns already block a Memo Out edit/delete via `usedBy`), MEMO_OUT_RETURN up (master has checked the Memo Out line outstanding under its lock).

The operation then runs in three steps:

1. If there is an acquire part, a short tx0 sets `SYNCING` and stores the op (revision r, H_old/H_mid/H_new, action). Master then sends `PUT r = H_mid` (H_old plus the acquire part). A refusal ends the op, sets `IDLE` and maps the error per row; nothing has changed. An unknown outcome returns `503 INVENTORY_UNAVAILABLE` ("nothing was saved") and the op is **abandoned** by re-drive (`PUT r+1 = H_old`, release-only).
2. tx1 runs today's engine body unchanged (numbering, lines, Memo Stock effects, status) and records `hold_revision`. If tx1 fails for a business reason (e.g. Memo Stock short), master compensates with `PUT r+1 = H_old`. That PUT only undoes this op's acquire part, so it cannot be refused.
3. If there is a release part, master sends `PUT = H_new` after tx1 commits. The user gets success. If the outcome is unknown, re-drive repeats the same revision until DONE, with the document `SYNCING` meanwhile; until then the extra quantity stays held (conservative, never oversold).

No HTTP call is made inside a database transaction. Re-drive happens on access, at start, and in a 60 s sweep (≤ 20 ops, 15 s lease, backoff ≤ 60 s, `STUCK` after 10 attempts, operator script `inventory-sync:redrive`). While a document is `SYNCING`, its writes and Memo Out Returns of it get `<CODE>_BUSY`. Drafts (ON), Submit, Revise and Reject call nothing; drafts are validated with the D17 pre-read.

**D20 — Master line model.** `reserve_line`, `memo_out_line` and `quotation_line` get `own_stock_id uuid NULL`, source `OWN_STOCK`, a CHECK that exactly one of `memo_stock_id` / `own_stock_id` is set for a stock line, and a unique key (document, own_stock_id). `memo_out_return_line` is unchanged: it reaches our stock through `memo_out_line.own_stock_id`. The Memo Out Return outstanding picker, its open index and the customer Memo Outstanding report include own-stock Memo Out lines. Divergence: Memo Out of Memo Stock still moves pending → reserved in `memo_stock` (existing SA-MO-14), while our stock uses its separate `memo_out` bucket.

**D21 — Credential and network.** New secret `master_inventory_service_token`, mounted as `MASTER_INVENTORY_SERVICE_TOKEN_FILE` in api-master and inventory. Inventory checks it constant-time on `/internal/v1/master/*` only. The two directions' tokens are never accepted for each other. The existing `inventory-master` network now also carries master → `backend-api-inventory:3301` (`INVENTORY_INTERNAL_URL`). There is no new network and no nginx change (nginx routes only `/api/inventory/`). Master gets **no** `depends_on` inventory (inventory already depends on master), so master starts and serves Memo-Stock-only work without inventory.

**D22 — Capacity (4 GB / 2 vCPU).** No container, worker, Redis or pool change. Master gets an outbound client with ≤ 4 keep-alive sockets and timeouts of 2 s (picker) / 5 s (batch, holds), a 60 s sweep, and an estimated +10 MiB RSS within its 384 MiB limit. Inventory internal routes are limited to ≤ 4 in flight (excess → `503 INVENTORY_BUSY`, retryable), each using one short transaction from the existing pool of 5. Per picker page: 1 master query + 1 HTTP + 1 inventory query. Per own-stock save: ≤ 1 batch read + ≤ 2 hold PUTs. Compose stays at 1.75 vCPU / 2880 MiB. Measure picker p95 with 5,000 available stocks and a 200-stock hold before claiming fit.
