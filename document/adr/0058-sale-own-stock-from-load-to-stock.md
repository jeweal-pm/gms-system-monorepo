## Context

The Sale page has two item buttons. **From Stock** opens the shared lot dialog but is restricted to Memo Stock (`memoOnly`; "inventory takes no own stock in Sale"). The stones that Load to Stock puts into `inventory.stock` can therefore not be sold. The owner noticed that From Stock is "not connected to Load".

Facts from the checkout (2026-11-23, branch `feat/23-11-26-stock-card`):

- Sale is a module of `backend-api-inventory` (ADR-0054). A line has `source` `RESERVE | STOCK` (`STOCK` = Memo Stock, by lot key `M*`), applied through an idempotent master call (`PUT /internal/v1/inventory/sale-consumptions/{saleId}`) driven by the local saga (`sale_sync_op`, shared `SyncDriver`). `SaleService` writes the Sale and its op row in one transaction (tx0), drives master, then completes in tx1.
- Own stock is `inventory.stock`: one row per Stock ID, buckets `on_hand / reserved / memo_out / sold / consumed`, `pcs = Σ buckets`, `lot_key = 'OS' || id` for every stock this round (owner 2026-11-21: own stock is not merged), index `stock_lot_open_idx` for FIFO candidates. The schema already allows `stock_hold.document_type = 'sale'` with kind `SOLD`, and `stock_hold_document` rows of type `sale`. No code writes them.
- The ledger `inventory.stock_movement` is append-only. Stock Card (ADR-0056) shows only kinds listed in `CARD_KINDS`; `card-kinds.ts` already contains `DOCUMENT_TYPES.sale` ("Sale", Stock ID visible, source `HOLD`) and a note that own-stock Sale adds its kind rows. Stock Card joins `stock_hold_document` for the date and the account of a `HOLD` document. Balance = `on_hand + reserved`; the test invariant is `Σ card-kind deltas of a stock = on_hand + reserved`.
- The lot pickers of Quotation, Reserve and Memo Out read master `fromStock.lots` (own stock first, then Memo Stock). `fromStock.lots` lists `sale` among its permitted grants, so a Sale user can already read own-stock lot rows by hand (security finding R2-F1 of INV-20261121-002: no Sale purpose, widening).
- Master's From Reserve search lists only Memo Stock Reserve lines (`memo_stock_id IS NOT NULL OR lot_key LIKE 'M%'`). A Reserve line over own stock (`reserve_line.own_stock_id` / `lot_key 'O*'`, `reserve_line_alloc.own_stock_id`, inventory `stock_hold` of type `reserve`) can never be sold, although `reserve_line.sold_*` and `reserve_line_alloc.settled_*` already exist.

## Decision

**D1 — Placement and line sources.** Own-stock Sale stays in `backend-api-inventory`, and own stock is consumed **locally**. No service, container, network, secret, volume, gateway or package is added. A Sale line has one of three sources: `RESERVE` (a Reserve line, Memo Stock or own stock), `STOCK` (Memo Stock lot; the name is unchanged so existing data, master consumption and the browser keep working; "MEMO_STOCK" in the request wording) and **`OWN_STOCK`** (new: an own-stock lot). `OWN_STOCK` names `lotKey` (`OS…` / `OL…`), never a Stock ID.

**D2 — Own-stock line.** Pcs and weight follow the stock-line rules (pcs or weight > 0, each ≤ the lot's available quantity, plus this Sale's own applied quantity on an edit), Sale Price > 0, one lot once per document (partial unique index). Save copies the attribute snapshot, `stockCount`, the newest Load reference (id and number) and the available quantity into the line without locks and holds nothing (D3 of ADR-0054). Available = Σ `on_hand` of the lot's ACTIVE stocks; stones held by Reserve or Memo Out are in other buckets and are not available.

**D3 — Consumption (local, FIFO, exact reversal).** At apply (Approve with approval ON; Save, Edit, Delete of an auto-approved Sale with approval OFF) inventory allocates each `OWN_STOCK` line to Stock IDs by ADR-0055 D5: candidates oldest first (`ref_doc_date`, `stock_id`), pcs and weight separately, increases take the next free quantity, decreases release the newest allocation first. In **one statement per step** it locks the old ∪ new stocks `FOR UPDATE` in id order (the lock order of `applyHolds`), checks `on_hand`, moves `on_hand → sold`, and appends ledger rows. The per-line, per-stock allocation is stored in `inventory.sale_line_alloc` (the existing table, extended with `own_stock_uuid`), which is what a void, edit or delete reverses exactly. Short stock refuses the whole operation with `409 SALE_SOURCE_SHORT` (per-line `exceeds_pending`) and changes nothing.

**D4 — Order of work and the saga.** Own-stock effects run in **tx0**, in the same transaction as the guarded Sale update and the op row. Master is called only when the Sale has Memo Stock or Reserve lines (applied or desired); a Sale with only `OWN_STOCK` lines never calls master and completes in that one transaction (no op row, `sync_state` stays `IDLE`). If master refuses (`SALE_CONSUMPTION_*`), `refuseOp` reverses the own-stock delta recorded in the op payload in the same transaction that marks the op refused, so no half-sold stone survives. The idempotency unit is the op `(sale_id, revision)` exactly as for Memo Stock; the own-stock part has no HTTP boundary and is atomic with the op row.

**D5 — Reserve interplay.** Own stock held by a Reserve is not available to From Stock (it is in `reserved`). Selling it is the job of **From Reserve**, which now also lists the open lines of own-stock Reserve lines. It works as for Memo Stock: the Sale consumes the Reserve line's open quantity; the Reserve stays APPROVED and becomes "used" (ADR-0054 D4/D7). Master settles `reserve_line.sold += q` and `reserve_line_alloc.settled` oldest first (ADR-0055 D5) and returns the per-Stock-ID rows (`source: "OWN_STOCK"`). Inventory, in **tx1** (the same transaction that completes the Sale), moves `reserved → sold` on those stocks, **reduces the Reserve's `stock_hold` (type `reserve`) by the same quantity** (a zero row is deleted), and writes the ledger. A release (edit, delete) reverses it, re-inserting the hold. Invariant: `stock_hold(reserve, R, S)` = the open quantity of the Reserve's allocation on `S`; a Reserve with a sold line is "used" and master refuses its edit and delete, so nothing else changes that hold. A Reserve whose hold is still being applied is refused as busy.

**D6 — The From Stock read for Sale.** A new inventory REST read `GET /api/inventory/v1/sale/stock-lots` (grant `sale:VIEW`, the same grant as `sale/reserve-lines` and `sale/options`) returns one list, **own stock first, then Memo Stock**, 50 per page, one opaque cursor, the same row shape and columns as the other lot pickers. Own stock is read locally (one statement on `stock_lot_open_idx`); Memo Stock lots come from master through one new internal read `POST /internal/v1/inventory/sale/memo-lots`, which reuses master's lot SQL and strips price and vendor. If master is down the page still returns own rows with `memoStock: "UNAVAILABLE"`. After the browser switches, master removes `sale` from the grants of `fromStock.lots` (closes R2-F1); the quotation / reserve / memo-out grants are not used by Sale and are not needed by it.

**D7 — Price.** The Sale unit price is entered by the user. An own-stock row carries the lot's Sale Price (`stock.sale_price`, company currency per price unit) so the UI prefills `salePrice ÷ Selling Rate` (2 dp, half-up; as is in the company currency; empty when the rate is not known yet), editable. Cost (`unit_cost_base`, `cost_amount_base`) and vendor never leave inventory through this read, and no price or vendor is returned for Memo Stock rows.

**D8 — Stock ID.** The picker and the Sale line show the Lot and the stone details and **no Stock ID** (an `OWN_STOCK` line stores `stock_id = ''`, like a Memo Stock lot line); the allocation rows keep the Stock IDs server-side. Reserve lines keep showing the Stock ID where they do today. Stock Card still shows the Stock ID on a Sale row (the registry of ADR-0056 is unchanged: the owner hides it only on Quotation, Reserve, Memo Out, Purchase and Memo Return).

**D9 — Ledger, Stock Card and Stock Value.** Two kinds are added to `stock_movement_kind_check` and to `CARD_KINDS`: `SALE_OUT` (book stock −q, from `on_hand` or `reserved`) and `SALE_OUT_REVERSAL` (+q), both `documentType: "sale"`, `effect: "MOVEMENT"`, `cost_delta_base = 0`. The Sale also writes a `stock_hold_document` header (`document_type 'sale'`: number, **document date**, **customer** as account) when it completes, so Stock Card shows an OUT row with the Sale number (link `/sale/sale/{id}`) and the customer name, and nets a deleted or edited-back Sale to zero. Balance falls by the sold quantity, so Stock Value's remaining value falls; the sold stone's Sale line becomes a "Last sale" candidate through the existing `sale_line.item_key` (no change to ADR-0057).

**D10 — Schema.** One additive migration `20261123120000_sale_own_stock` (after `20261123110000_stock_value`): widen `sale_line` source/reference CHECKs, add `load_id`, `load_doc_no`, a partial unique index per own lot; extend `sale_line_alloc` with `own_stock_uuid` (FK `stock`), nullable `memo_stock_id`, an exactly-one CHECK and a unique key; widen `stock_movement_kind_check`. Applied migrations are not edited. Rollback is a script that refuses once an own-stock line, allocation or `SALE_OUT*` ledger row exists (the ledger is append-only: forward-fix only after the first applied own-stock Sale).

**D11 — Capacity.** Inventory limits unchanged (0.20 vCPU / 256 MiB / heap 160 MiB, pool 5 + authz 1). Bounds: ≤ 200 lines per Sale (own ≤ 200), ≤ 500 candidate stocks per lot, ≤ 2,000 locked stocks per transaction (`422 STOCK_LOT_TOO_LARGE`), the picker ≤ 50 rows and ≤ 2 statements plus one master call (2 s, shared ≤ 4-socket client). The own-stock step is ≤ 6 statements for any number of lines. Compose total stays **1.75 vCPU / 2880 MiB**.

## Alternatives

| Alternative | Why not chosen |
|---|---|
| **Reuse master `fromStock.lots` unchanged** (the minimum frontend change: drop `memoOnly`) | Zero new endpoint, but the Sale picker would route browser -> master -> inventory for stock that inventory owns, would keep Sale on master's quotation / reserve / memo-out grant list (R2-F1 stays), cannot show an own-stock row while master is down, and cannot add Sale-only fields (prefill price). Kept as the **fallback** if the owner prefers it (SQ-SO-05): the frontend would only remove `memoOnly` and apply D3 unchanged. |
| Consume own stock through master (a hold saga like Reserve / Memo Out, `stock_hold` type `sale`, kind `SOLD`) | Inventory owns both the document and the stock; a master round trip and a second saga add failure modes for nothing. `stock_hold` is unique per (document, stock), so one stone taken by an own line and a Reserve line of the same Sale would collide. |
| Master call always, with an empty set for own-only Sales | Simpler driver, but own-stock Sale then needs master up (503 `SYNC_PENDING` otherwise). D4 keeps own-only Sales independent of master. |
| Consume after master (tx1) for own-stock lines | A local refusal after master applied needs a master compensation call. Local first has a trivial same-database compensation. Reserve lines cannot go first (the per-Stock-ID rows come from master), so they settle in tx1 where the quantities cannot be short by invariant (D5). |
| Write `stock_hold` rows (type `sale`) as the allocation | Loses the line link and the on-hand / reserved origin needed for an exact reversal. `sale_line_alloc` already exists for Memo Stock and gains the own-stock key. |
| Rename source `STOCK` to `MEMO_STOCK` | A contract change for no behaviour; rows, master consumption and the form already use `STOCK`. A mapping table in the contract is enough. |
| Record cost of goods in `cost_delta_base` | Every hold kind writes 0 and Stock Value reads cost from the stock row; the Sale Report module owns margin. Offered as SQ-SO-06. |
| Include Reserve own-stock lines later | A reserved own stone could then never be sold except by deleting the Reserve. Kept in this revision as phase B, ordered after phase A, so the owner can stop after A. |

## Consequences and capacity

- **Inventory, additive migration** `20261123120000_sale_own_stock` (D10). **Master, additive:** one internal read (`sale/memo-lots`); From Reserve search, prepare and consumption accept own-stock Reserve lines (an index for open own lines, the allocation `source`, a busy refusal); `sale` leaves `fromStock.lots` grants. No master table change except one partial index.
- **Frontend (small):** the Sale binding of the shared lot dialog uses the new read and no `memoOnly`; `OWN_STOCK` source, price prefill, source line "from {Load No.}", two new error texts. Sale UI sections touched: T-03, T-09, item table first column / Location, P-02, Interaction (stock move text), Out of scope (own stock removed). No new component.
- **Compatibility:** existing Sale documents and master contracts are unchanged; `source` gains one value; `fromStock.lots` loses the `sale` grant only after the frontend switch. Old queued ops without `own` payload keep working.
- **Rollback:** before the first applied own-stock Sale, drop the objects with the rollback script; afterwards forward-fix only. The browser change is a pure revert.
- **Infra / DevOps:** none (no container, route, volume or variable; nginx already routes `/api/inventory/`). **Risks:** (1) a crash between tx0 and master leaves own stock sold while the op is `PREPARED`; the re-driver or the refusal path resolves it within the 15 s lease / 60 s sweep, and Stock Card may show the OUT row meanwhile; (2) a drift in tx1 for a Reserve line leaves the op `CONFIRMED` (`503 SYNC_PENDING`, `sync:redrive`), expected never to occur; (3) FIFO across several stocks gives one line several allocation rows (stored); (4) own stock is not merged this round, so a lot is one stock and a lot picker row is one Stock ID.

## Acceptance and approval

Observable checks (IT-SO-* in [testing](../apps/backend/inventory/sale-own-stock/testing.md)):

- Load 5 pcs of a stone, open Sale › From Stock: the stone appears first in the list (before Memo Stock), with no Stock ID; pick 2 pcs, the Sale Price is prefilled; Approve: Load stock shows on-hand 3, sold 2, Stock Card shows an OUT 2 row "Sale" linking to the Sale with the customer name, Stock Value balance falls by 2.
- A Sale with only own-stock lines approves while master is stopped. A Sale with one own and one Memo Stock line whose master call is refused leaves the own stock unchanged.
- Two Sales of the last 3 pcs: one succeeds, the other `SALE_SOURCE_SHORT`, nothing changed. Delete or edit-down of an auto-approved Sale returns the pieces; its Stock Card row nets to zero.
- A Reserve of 2 pcs of own stock then a Sale From Reserve of 1 pc: Reserve line sold 1, stock `reserved 1 / sold 1`, `stock_hold(reserve)` 1, Stock Card OUT 1; deleting the Sale restores all three.
- A user with only `sale:VIEW` reads own and Memo Stock lots from `sale/stock-lots` and no longer from `fromStock.lots` (after BE-SO-009); no price, cost or vendor in the rows.

## Refinement notes on earlier ADRs

- **ADR-0054 D11 (own stock, phase 2):** realised here. The "tx0 under `FOR UPDATE` before the master call, reversed in tx1′ on a refusal" intent is D3/D4. The price prefill intent ("Load Sale Price ÷ Selling Rate, editable") is D7. The "From Reserve line whose Reserve holds own stock must reduce that Reserve's `stock_hold` in inventory and its master Reserve line in one apply" is D5: master line and inventory hold are changed in one saga op (master PUT, then tx1), not in one database transaction.
- **ADR-0055 D5/D7:** "Future Sale own stock allocates locally with the same D5 rules" is D3 (FIFO, newest-first release, `sale_line_alloc`). D9 is unchanged for the pickers (no Stock ID on the lot picker row); a Sale `OWN_STOCK` line stores none.
