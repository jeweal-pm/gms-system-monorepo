## Context

Better Auth currently issues an opaque database session and the gateway fetches auth's uncached session context on each request. ADR-0016 makes grant changes effective on the next request. License-server refresh and outage grace follow ADR-0013, a *different* freshness policy. GMS §2/§7 asks for local public-key JWT verification and a 15-minute access token. A JWT with embedded permissions would silently weaken the next-request rule.

## Decision; configurable offline policy selected

1. Keep Better Auth as credential/session authority. Auth alone issues a separate user access JWT using EdDSA, `kid`, `iss` from configuration, `aud=gms-domain-api`, `sub=user.id`, `sid=session.id`, `jti`, `iat`, `nbf`, `exp<=15 minutes`. Publish only public keys at auth JWKS. Domain APIs permit only the configured algorithm, issuer and audience; reject unknown `kid`, stale keys, invalid signature and clock-expired tokens. Do not reuse the EdDSA license-server token as a user token.
2. Auth owns a dedicated one-time opaque refresh credential (7-day initial lifetime proposed), stored hashed at rest with family/session association, atomic rotate-on-use, reuse detection and family revocation. Browser receives host-only Secure HttpOnly SameSite=Lax access and refresh cookies; refresh cookie Path is limited to auth refresh route. Auth expires them on logout/password reset/deactivation, and only one active family/session per user remains per approved single-session behavior. Concurrent tabs use a client single-flight refresh; a losing concurrent refresh receives a normal reauthenticate response unless an approved bounded overlap policy is documented. Refresh is never silently retried after an ambiguous commit.
3. **Local state:** each domain verifies JWT locally, then executes an indexed read of an auth-owned **read-only authorization view** on the same PostgreSQL cluster (allowed by GMS §2.2). The view exposes only user/session active state, current local license record, menu/action grants, location scopes and a permission version; each service gets SELECT on the view, no auth-table writes. It must be transactionally current with grant/session/account changes. There are no stale grant claims in JWT. Price fields require the live `PRICE` grant before serialization. On DB/view failure, reject protected operations; do not use a stale in-memory allowlist. Sensitive mutations recheck inside the write transaction where read/write DB isolation permits; otherwise validate immediately before mutation and document the remaining race.
4. **Freshness:** local grant, account and session changes must deny the next protected request through the live view. For a remotely revoked license, the owner selected next-request denial **when the license-server is reachable**. A 15-minute JWT or shorter refresh timer alone cannot provide this. During a network outage, remote revocation cannot be observed; the owner explicitly requested a configurable grace period, so next-request remote revocation is not guaranteed while offline.
5. **Proposed license check and offline policy:** after local JWT and view checks, every protected domain request obtains a fresh license decision through a narrow authenticated auth endpoint; auth performs a bounded online lookup and validates the license-server's signed result. An explicit revoked/expired/missing result denies immediately and is never overridden by grace. For a transient connection timeout or server 5xx only, `LICENSE_OFFLINE_GRACE_DAYS` is an integer from 0 to 2, default **2** under the separately approved [license contract revision 2](../spec/gms-license-server-contract-rev2.md). `0` returns 503 and denies immediately. A positive value permits access only if the last successful signed **eligible** result belongs to the same instance/user and its signed expiry, natural license expiry and `lastSuccessfulCheckAt + grace` are still in the future; the timer never slides on failed checks. The opt-in v2 license token expires three days after issue and carries signed `contract_version: 2`. No verified result, bad signature, key/configuration error, clock uncertainty, or expired token fails closed. Record fallback usage without exposing the token. The worst-case remote revocation lag during a continuous outage is the configured grace, capped by token expiry. This is an explicit exception to GMS §2's no-per-request-auth-call rule and revises ADR-0013's 24-hour refresh/seven-day grace for protected requests after cutover. Measure p95, request volume and remote capacity. The production license-server is not yet available, so route cutover remains blocked.
6. Package/feature entitlement claim structure is **not established** in the current license token; retain existing binary eligibility and per-user menu grants. Any new feature/package entitlement requires a separate license-server contract, mapping and ADR before enforcing it.
7. Every cookie-authenticated mutation (tRPC, REST, upload, refresh and logout) requires trusted `Origin`/Fetch Metadata and a CSRF token or enforced non-simple custom header; GET never changes state. Trust forwarded headers only from Nginx. Cookies are never in localStorage; personalized responses are `private, no-store`. Refresh and login are rate limited. Critical authorization failure is 503 and fails closed; missing/expired authentication is 401; known denied grant/license is 403 or the existing activation-required state contract. Preserve the existing three wrong-key attempts/one-minute activation lockout.
8. JWKS cache is bounded (proposed maximum 2 keys/10 minutes), refreshes once on unknown kid with throttling, rejects if no valid key, and overlaps old/new keys for at least the access-token lifetime plus clock skew. Operational key rotation requires an approved runbook and observation.

**Owner approval and remaining blocker:** on 2026-10-20 the owner approved SA revision 1 and then the separate [three-day-token/0–2-day-grace revision 2](../reviews/sa/2026-10-20-gms-license-contract-rev2.md) for customer-backend code. External license-server implementation, compatibility and capacity evidence remain unavailable; see [GP-LIC-01](../task/todo/gms-platform-migration.md). Until those dependencies are verified, do not move protected authorization out of the gateway.

## Data, transaction and rollback

Auth adds a hashed `RefreshCredential` family/rotation model and an auth-owned read-only projection/view (see [ER diagram](../apps/backend/auth/gms-platform/database-diagram.md)). Never expose refresh hashes in the view. Rollout creates nullable/new tables/view first, dual checks old and new paths in a nonproduction parity phase, cuts over by path, then removes the old gateway dependency only after all sessions/flows pass. Rollback routes traffic to old gateway and retains new records inert; do not restore old secrets or clear user accounts. If refresh semantics cannot be implemented safely against Better Auth 1.7.7, stop and revise this ADR rather than substituting a sliding session silently.

## Alternatives and capacity

JWT-contained grants alone are cheapest but violate next-request revocation. A read-only view adds an indexed database read per protected request (current gateway already asks auth, which queries grants). Budget that load against the 40-connection database limit and measure p95; grant rows are bounded by catalog. A per-request online license check adds auth and remote-server availability/latency coupling. A revocation feed needs delivery acknowledgements, reconnect and durable replay; it cannot promise next-request revocation across a network partition while retaining offline grace. A longer grace improves outage availability but increases the maximum period during which an offline instance may still honor a remotely revoked license.

## Acceptance and approval

The owner selected next-request local revocation, online remote-license revocation, and configurable offline grace (default 2 days, 0 disables it), then approved this ADR in [SA revision 1](../reviews/sa/2026-10-20-gms-platform-migration-rev1.md) and the license-contract revision 2 amendment. GP-AUTH-05 cutover still depends on the actual external implementation and capacity. Tests must show local and reachable-remote revocation on the next request; explicit revoked status never using grace; 0/1/2-day outage bounds; non-sliding fallback, signed expiry, invalid signature and no-cache denial; key rotation, CSRF, refresh replay/concurrent tabs, and 4 GB/2 vCPU load. No production implementation or deployment is implied by the ADR's Accepted status.
