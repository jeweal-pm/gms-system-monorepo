# ADR-0012: เปลี่ยน Flow Login เป็นแบบล็อกบัญชีชั่วคราวเมื่อใส่รหัสผิด 3 ครั้ง

- **Status:** Accepted
- **Date:** 2026-10-09
- **Deciders:** Jakapong Chan-o ( PM )

## Context

Flow login เดิมไม่มีการจำกัดจำนวนครั้งที่ใส่ password ผิดต่อบัญชี
มีเพียง rate limit ระดับ API (ดู [Login Requirements: Security](../spec/0002-login-requirements.md))
ซึ่งป้องกันการยิงถี่ ๆ แต่ไม่ได้บอก user ว่าเหลือโอกาสอีกกี่ครั้ง
และไม่ได้หยุดการเดารหัสผ่านของบัญชีใดบัญชีหนึ่งโดยตรง

จึงออกแบบ flow ใหม่ทั้งหมด ให้ล็อกบัญชีชั่วคราวเมื่อใส่ password ผิดครบ 3 ครั้ง
และให้หน้า Login แจ้งสถานะกับ user ชัดเจน (เหลืออีกกี่ครั้ง / ต้องรออีกกี่วินาที)

นอกจากนี้ requirement ต้องการ password policy แบบง่าย คือ **อย่างน้อย 4 ตัวอักษร**
ไม่บังคับตัวพิมพ์ใหญ่ ตัวพิมพ์เล็ก หรือตัวเลข (ดู [Password Policy](../spec/0003-password-policy.md))
ทำให้รหัสผ่านเดาง่ายขึ้น การล็อกบัญชีจึงเป็นกลไกหลักที่ชดเชยส่วนนี้

## Decision

1. ใส่ password ผิด **3 ครั้งติดกัน** → ล็อกบัญชี **1 นาที**
2. ระหว่างถูกล็อก API ตอบ `423 Locked` พร้อมเวลาที่เหลือ หน้า Login นับถอยหลัง
   และเปิดให้กด Login ได้อีกครั้งเมื่อครบเวลา
3. ใส่ผิดแต่ยังไม่ครบ 3 ครั้ง → API ตอบ `401` พร้อมจำนวนครั้งที่เหลือ
4. Login สำเร็จ → reset ตัวนับ, สร้าง session แล้ว redirect ไปหน้า Home
5. บันทึกทุก login attempt (success / failed) ลง database

ข้อมูลที่ต้องเพิ่มใน user:

| Field | ความหมาย |
|-------|----------|
| `failed_login_count` | จำนวนครั้งที่ใส่ผิดติดกัน |
| `locked_until` | เวลาที่ปลดล็อก (`null` = ไม่ถูกล็อก) |
| `last_login_at` | เวลาที่ login สำเร็จล่าสุด |

และตาราง login attempt สำหรับเก็บประวัติการ login

Flowchart และ sequence diagram อยู่ที่
[Login Flow Diagrams: ข้อ 1 และ 2](../diagram/login-flow.md)

ทางเลือกที่พิจารณา:
- **Option 1: ใช้ rate limit ระดับ API อย่างเดียว (flow เดิม)**
  ทำง่าย แต่ user ไม่รู้ว่าเหลือกี่ครั้ง และไม่ได้ป้องกันการเดารหัสต่อบัญชี
- **Option 2: ล็อกบัญชีถาวรจนกว่า admin จะปลดล็อก**
  ปลอดภัยสูง แต่เพิ่มภาระ admin และ user ใช้งานต่อเองไม่ได้
- **Option 3: ล็อกชั่วคราว 1 นาทีเมื่อผิดครบ 3 ครั้ง (เลือก)**
  สมดุลระหว่างความปลอดภัยกับการใช้งาน user กลับมา login เองได้โดยไม่ต้องติดต่อใคร

## Consequences

**ข้อดี**
- ชะลอการเดารหัสผ่านต่อบัญชีได้ชัดเจน
- User รู้สถานะของตัวเอง (เหลือกี่ครั้ง / ต้องรออีกกี่วินาที)
- มีประวัติ login attempt ไว้ตรวจสอบย้อนหลัง
- Password policy ง่าย user ตั้งและจำรหัสผ่านได้สะดวก

**ข้อเสีย / ความเสี่ยง**
- **Password อ่อน:** รหัส 4 ตัวอักษร เช่น `1234` เดาได้ง่าย
  ความปลอดภัยของบัญชีขึ้นกับการล็อกและ rate limit เป็นหลัก
- **User enumeration:** ถ้าตอบ `401 + จำนวนครั้งที่เหลือ` หรือ `423` เฉพาะ email ที่มีอยู่จริง
  ผู้โจมตีจะรู้ได้ว่า email ไหนมีบัญชี ควรตอบรูปแบบเดียวกันสำหรับ email ที่ไม่มีในระบบ
- **Lockout DoS:** คนอื่นที่รู้ email สามารถใส่ผิดซ้ำ ๆ เพื่อล็อกบัญชีของ user ได้
  (ผลกระทบจำกัดเพราะล็อกแค่ 1 นาที)
- ล็อก 1 นาทีแล้ว reset ตัวนับ ทำให้เดาได้ประมาณ 3 ครั้ง/นาที/บัญชี
  จึงยังต้องคง rate limit ระดับ API ไว้คู่กัน
- ต้องเพิ่ม field ใน user และตาราง login attempt (migration ใหม่)
- ต้องตรวจสอบว่าทำงานร่วมกับ Better Auth ได้ (ดู ADR-0008) เช่น ใช้ hook / plugin
  ก่อนและหลัง sign-in แทนการเขียน endpoint login เอง
- การนับ `failed_login_count` ต้อง update แบบ atomic เพื่อกัน request พร้อมกันนับพลาด

**ทางลดความเสี่ยงที่ควรพิจารณา**
- ตอบข้อความเดียวกันทั้งกรณี email ไม่มีอยู่และ password ผิด
- เพิ่มระยะเวลาล็อกเป็นขั้น ๆ ถ้าถูกล็อกซ้ำหลายรอบ
- แจ้งเตือน user ทาง email เมื่อบัญชีถูกล็อกบ่อยผิดปกติ
- ห้ามใช้รหัสผ่านที่พบบ่อย เช่น `1234`, `0000`, `abcd` (ไม่บังคับตาม requirement ตอนนี้)
