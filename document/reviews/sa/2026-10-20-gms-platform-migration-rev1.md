## Proposed architecture and decision points

Keep tRPC for existing auth/master app data, hosted by each domain service behind one Nginx origin. Keep Better Auth as credential and database-session authority. A separate <=15-minute EdDSA access JWT and one-time rotating refresh credential serve domain APIs; the license-server's signed token never becomes a user access token. Each domain verifies the JWT locally and checks a narrow auth-owned read-only PostgreSQL view for current local account/session/grants. Existing account deactivation, logout and grant changes then deny the next protected request. Domain APIs enforce exact actions and PRICE masking; frontend menu visibility remains presentation only.

The owner also wants a remotely revoked license denied on the next request while the license-server is reachable. A proposed private auth check performs an online signed status lookup for each protected domain request. During a transient outage only, `LICENSE_OFFLINE_GRACE_DAYS` selects immediate denial at `0` or bounded use of a previously verified eligible signed result; the proposed allowed range is 0–7 days and **default is 2**. The deadline never slides after a failed check and cannot exceed signed expiry. Explicit revoked/expired/missing status, bad signature and wrong identity never use grace. A remote revocation **cannot** be learned during an outage; at the default it can remain effective locally for up to two days or less if the signed token expires first. This is the stated tradeoff, not a next-request guarantee while disconnected.

The approved online license path is an explicit exception to [GMS §2](../../gms-platform-spec.md) (which otherwise forbids per-request auth calls). The revised [ADR-0013](../../adr/0013-per-user-license-with-signed-token.md) freshness/grace rule still needs an actual production [license-server contract](../../spec/gms-license-offline-policy.md). The remote service does not exist in this checkout; mock mode cannot prove the proposed guarantee. **GP-AUTH-05 and every dependent protected-route cutover remain blocked** until the contract and service-level/capacity evidence are approved. Preserve current license behavior during independent implementation.

The target master service adapts the existing partner service and migrates procedures and data ownership in phases; existing `partner`/`stone` tables stay put until separately verified migration. Inventory is a new service and stock domain, but its first product/UI slice, permission keys and posting flow need separate approval. Redis/worker and S3/Garage are later feature/profile gates, not automatically enabled. The proposed initial deployment profile is `db-local + fs`; a customer profile choice and measured full-stack fit are still needed.

## Boundaries and unresolved evidence

- **Capacity:** target `db-local + fs` hard memory caps total 3040 MiB; 4096 − 3040 = 1056 MiB nominal host margin, roughly 556 MiB after the spec's ~500 MiB OS/Docker estimate. This is not a measured production fit. CPU caps, worker peaks, PostgreSQL pools, auth view and per-request license-server latency must be measured before enabling new services. Production remains 4 GB RAM / 2 vCPU total.
- **Contract:** the exact Better Auth 1.7.7 JWT plugin behavior, cookie paths, refresh concurrency, public JWKS rotation and private license check require version-locked prototypes/contracts. The existing license-server API is a draft with no production server, so remote status capacity/SLA is unknown. `@gms/storage`, Hono, Redis/BullMQ and new service images are proposed, not installed.
- **Newly identified GP-LIC-01 blocker (2026-10-20):** the existing [license-server API draft](../../spec/0005-license-server-api.md) sets signed token `exp = iat + 24 hours`. The approved offline formula caps fallback at signed expiry, so default two-day grace cannot be delivered with that token. An approved longer-lived signed eligibility proof or separate offline lease contract is required; no change to the existing external API is implied by approval of this SA revision.
- **Data:** auth refresh tables/view, `partner`/`stone` ownership, local named-volume to bind-mount move, company logo bytes and inventory schema all need additive migration, counts/checksums, backup/restore and rollback plans before cutover. No existing customer data is assumed safe to rewrite or delete.
- **Deployment:** exact customer DB/file profile, host CPU architecture, image digests, ingress/TLS, backup target, RPO/RTO, observation window, maintenance window and remote GitHub settings are not selected by this document. No deployment is authorized.
- **Scope:** existing accepted UI feature TODOs and `document/task/frontend-latest.md` remain separate. No inventory screen, worker job, S3/Garage profile or package install is authorized by a general approval of this architecture unless its own TODO/revision is explicitly selected.

## Approval and continuation

The owner approved this SA revision and its stated ADRs/exception on 2026-10-20 for work without license-server blockers. The remote license-server dependency and measured capacity remain implementation blockers. Work proceeds in narrow order: independent auth prototypes and infra prerequisites, domain procedure parity, frontend cutover after its prerequisites, then separately selected inventory/worker/storage features. Each code handoff needs its relevant unit/integration tests and both focused security reviews; production deployment needs its own explicit authorization.

No application code, Compose, CI workflow, migration, image, browser session or production service was changed or run for this SA review. The independent infra/DevOps documents are static proposals, not operational evidence.
