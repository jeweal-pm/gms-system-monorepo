## Current state and target inventory

The locally updated `.github/workflows/ci.yml` runs `pnpm lint`, `pnpm build`, `pnpm typecheck`, the four existing workspace Vitest scripts serially, and base/dev Compose syntax checks on dev/master pushes and PRs. `PARTNER_LIVE_TESTS=0` leaves opt-in live partner integration tests outside this gate. Existing full action pins are recorded in [GitHub configuration](github-configuration.md); no new action pin is introduced here.

Current frontend runs `next start`, not the target standalone `node server.js`. Neither `api-inventory` nor `worker` has source, package, or Dockerfile in this checkout. `nginx` and `redis` are proposed upstream runtime images, not local app build targets. The target can retain tRPC and Better Auth only through the SA-approved service/token migration; do not infer target source paths from proposed service names.

## Variable and secret contract

**Current GitHub settings:** `ENABLE_IMAGE_PUBLISH` (repository variable, required only for explicit publish, exactly `true`); `IMAGE_NAMESPACE` (repository or `container-publish` environment variable, optional; currently defaults to lowercased `github.repository`); automatic `GITHUB_TOKEN` (publish job only needs `packages: write`). Existing `container-publish` environment protections must be configured by the owner. The proposed `gms` namespace is a future value for `IMAGE_NAMESPACE`, not a new variable. No custom CI secret is required for build-only work.

**Proposed test-only settings:** a future nightly managed PostgreSQL integration check needs a **dedicated disposable test database endpoint, read-only CA bundle, and scoped test credentials** in a protected environment. Exact secret names and runner/network access remain pending infra/backend contract; no production DB URL belongs in PR CI. Local PostgreSQL 16/18 and Garage test instances should use isolated CI containers and disposable credentials defined by approved test fixtures, without deployment credentials.

**Runtime-only settings:** the target spec's Appendix C names `DATABASE_URL`, `DATABASE_URL_REPORTS`, `DATABASE_URL_MIGRATIONS`, `DB_SSL`, `DB_SSL_CA_FILE`, `DB_POOL_MAX`, frontend `INTERNAL_API_URL_AUTH`, `INTERNAL_API_URL_MASTER`, `INTERNAL_API_URL_INVENTORY`, `NEXT_TELEMETRY_DISABLED`, and storage `STORAGE_DRIVER`, `STORAGE_FS_ROOT`, `STORAGE_URL_SECRET`, optional `STORAGE_URL_SECRET_KID`, `STORAGE_PUBLIC_BASE_URL`, `STORAGE_UPLOAD_MAX_BYTES`, `STORAGE_EXPORT_TTL_DAYS`, plus `S3_*` variables only for an approved S3 profile. `DATABASE_URL_MIGRATIONS` belongs only to a one-off migration job, never an application container. Auth signing/refresh key names, Redis credential variable names, service-private credentials, target deployment variable/secret names, and customer backup credentials are **unresolved contract items**, not invented active settings. SA/backend/infra must specify them before wiring workflows or Compose. For `db-managed`, infra specifies provider limit, verified TLS CA and least-privilege role; `db-local` uses its own approved role/secret configuration. Never pass runtime secrets as Docker build args, put customer-specific values in `NEXT_PUBLIC_*`, or log resolved credentials.

The [proposed license offline policy](../spec/gms-license-offline-policy.md) adds runtime-only `LICENSE_OFFLINE_GRACE_DAYS` (integer 0–7, default 2) to auth. Record its value per customer and release; do not bake it into an image or `NEXT_PUBLIC_*`. `0` denies when status cannot be checked; a positive value permits only bounded signed fallback. The final private check, remote service-level and GMS §2 exception must be approved before adding it to a release variable contract.

The existing partner runtime keys `PARTNER_DATABASE_URL`, `PARTNER_SERVICE_TOKEN`, `PARTNER_SERVICE_URL` remain necessary for the old release set until its approved cutover. The current CI-only literal `PARTNER_SERVICE_TOKEN=ci-compose-config-validation-only-not-a-secret` is for `docker compose config` interpolation; it must not be used at runtime. The target runtime contract does not delete these settings until the old services and compatibility traffic are retired.

## Ordered release, readiness, and rollback proposal

1. **Before rollout:** record selected customer profiles (db-local/db-managed and fs/s3), data residency, backup target, RPO/RTO, actual host CPU architecture, free RAM/disk/CPU, DB connection ceiling, and measured complete Compose limit sum including OS and swap headroom. Infra approves image/Compose hardening and storage/DB backup restoration; SA approves data ownership, token/refresh/revocation and tRPC topology; backend supplies additive migration scripts and contract compatibility; frontend supplies same-origin/BFF migration. The SA feasibility review alone is not approval.
2. **Prepare and preserve data:** take and verify a restorable backup or restore drill for selected profile. Record current release manifest and image digests. Use expand → migrate → contract: apply backward-compatible additive schema/role changes with a one-off `migrate-<service>` job **before** starting the new service. Backend owns migration commands and checksums; deployment orchestration cannot guess cross-service order. Change auth/partner Dockerfile commands to stop auto-migrating only as part of the approved handoff, so parallel startup cannot race a migration.
3. **Stage compatibility:** deploy upstream Redis/Nginx and new services only within infra's measured budget. Route only approved paths to ready target services; leave gateway/partner paths and image set active until clients and data are fully migrated. Use `GET /readyz` for APIs and `GET /healthz` for frontend as the target spec requires. Confirm auth session/token issuance, refresh/revocation behavior, authorization/license checks, SSR, uploads/downloads, queue handling, and customer profile path with bounded smoke checks. Nginx route switches need a documented return route to the old service; any single-host traffic split or canary requires a concrete infra design rather than assuming load-balancer capacity.
4. **Promotion gate:** the complete image set, one-off migrations, selected profile Compose config, readiness and smoke checks, expected p95 and resource/queue observations must pass. Monitor errors, DB connection usage, memory/CPU, queue wait, disk, and backup status. Keep old images/config and compatibility schema through a defined observation window before contraction; choose that window in the approved rollout plan. Partial image publish, missing migration evidence, degraded auth/license enforcement or exhausted capacity blocks promotion.
5. **Rollback:** stop routing new traffic and restore the prior known-good Nginx/Compose config and **prior digest-pinned app images**. Keep additive database changes so old code remains compatible; never auto-run destructive down migrations. Jobs/files created during transition need SA/backend-approved idempotency and reconciliation rules before rollback is declared safe. If data ownership physically moved or a destructive schema step ran, simple image rollback is unavailable: use a tested restore/fail-forward runbook with recorded RPO/RTO and explicit operator decision. Keep backup snapshots and off-server copies protected from production delete credentials. Do not claim a full rollback until session/token, license, files, queue and database state have been checked.
